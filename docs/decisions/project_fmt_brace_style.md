# 포매터의 중괄호 리터럴 스타일과 주변 포매터의 구성 철학

작성일 2026-11-11. `cyber fmt`(`src/format.zig`) 규칙을 정하면서 적어 둔 것.

## 개요

- `cyber fmt`는 `Type{x=1, y=2}`처럼 타입 이름에 중괄호를 붙이고 안쪽 여백을 두지 않는다.
- 이 형태는 "타입 이름을 호출하듯 값을 만든다"는 계보(C99 → Go · C++11)에서 왔다.
  `foo(...)`와 `Bar{...}`를 같은 맥락으로 읽는 것이 설계 의도에 맞다.
- JavaScript의 `{ x: 1, y: 2 }`는 타입 이름이 없는 독립된 값이라 계보가 다르다.

## 유래

| 시기 | 언어 | 형태 | 의미 |
|---|---|---|---|
| K&R | C | `struct P p = {1, 2};` | 선언에 딸린 초기화 목록 |
| 1999 | C99 | `(struct P){.x = 1, .y = 2}` | 식 자리에서 쓰는 복합 리터럴, 지정 초기화 |
| 2009 | Go | `P{X: 1, Y: 2}` | 캐스트 괄호를 떼고 타입을 앞에 붙인 composite literal |
| 2011 | C++11 | `P{1, 2}` | 생성자 호출 `P(1, 2)`의 대체 표기 |
| 2015 | Rust | `P { x: 1, y: 2 }` | 구조는 같고 포매터 관례만 다름 |
| 2016~ | Zig | `P{ .x = 1, .y = 2 }` | C99 지정 초기화의 `.x =`를 유지 |
| — | Cyber | `P{x=1, y=2}` | Go의 붙여 쓰기 + `=` 구분자 |

## 핵심 디자인: 중괄호가 무엇의 경계인가

포매터마다 공백 규칙이 다른 것은 취향이 아니라 중괄호를 무엇으로 읽느냐의 차이다.

- 인자 목록으로 읽는 쪽 (Go, C++11, Cyber): `{`는 앞의 타입에 딸린 것이다. 함수 호출의 `(`와 같이
  이름에 붙이고 안쪽도 붙인다. clang-format의 `Cpp11BracedListStyle` 옵션 설명이 이 관점을 그대로
  적고 있다. 켜면 중괄호 목록을 "그 자리에 함수 호출이 있었을 때와 똑같이" 배치한다.
- 독립된 값으로 읽는 쪽 (JavaScript, Prettier): 객체 리터럴은 타입 이름 없이 혼자 서는 값이고
  블록 `{ ... }`와 같은 기호를 쓴다. 중괄호가 값의 경계이므로 안쪽에 여백을 둔다
  (`bracketSpacing` 기본값 true).
- 중간 (Rust, Zig): 타입은 앞에 오지만 안쪽 여백을 둔다. Rust는 `P {`처럼 이름과도 띄워
  블록 문법(`if x {`)과 모양을 맞추고, Zig는 이름에는 붙이고 안쪽만 띄운다.

## 주변 포매터의 구성 철학

| 포매터 | 설정 | 줄바꿈 | 정렬 | 안전장치 | 한 줄 요약 |
|---|---|---|---|---|---|
| gofmt | 없음 | 작성자 것(재배치 안 함) | 탭 기반으로 주석 · 필드 정렬 | — | 논쟁을 없애는 것이 목적 |
| zig fmt | 없음 | 끝 쉼표 유무로 작성자가 지시 | 일부 | — | 컴파일러와 파서 공유, 문법 이전 수단 |
| rustfmt | 있음(기본값이 스타일 가이드) | 폭에 맞춰 재배치 | 없음 | — | 가이드 문서가 규범, 도구는 구현 |
| Prettier | 소수 | 폭에 맞춰 전부 재배치 | 없음 | — | 원본 모양을 버리고 다시 그림 |
| Black | 거의 없음 | 폭에 맞춰 재배치, 끝 쉼표 존중 | 없음 | 전후 AST 비교 | "타협하지 않는" 한 가지 모양 |
| clang-format | 매우 많음 | 폭에 맞춰 재배치(벌점 최소화) | 옵션 | — | 기존 코드베이스의 관례를 재현 |

여기서 갈리는 축은 셋이다.

1. 줄바꿈의 주인: 작성자(gofmt, zig fmt)인가 도구(Prettier, Black, rustfmt)인가.
2. 설정의 유무: 하나의 모양을 강제하는가, 팀 관례를 담는가.
3. 의미 보존의 증명: 믿는가(대부분), 검사하는가(Black).

## 결정

`cyber fmt`는 gofmt · zig fmt 쪽에 서고, 안전장치는 Black에서 가져온다.

- 줄바꿈은 작성자 것이다. 줄을 합치거나 나누지 않는다.
- 설정은 없다. 들여쓰기는 4칸이다.
- 출력은 다시 파싱해 원본과 AST · 주석이 같을 때만 내보낸다.
- 중괄호: `{` 뒤와 `}` 앞의 공백을 없앤다. 타입 이름과 `{` 사이는 쓴 그대로 둔다.
  근거는 저장소 관례다. 여는 쪽은 붙인 곳 858 대 띄운 곳 21, 닫는 쪽은 910 대 72였다.
- 리터럴 필드의 `=`는 문장 수준의 `=` · `:=`와 같이 양쪽을 띄운다: `Vec2{x = 1, y = 2}`
  (2026-11-12 사용자 결정. 그 전에는 쓴 그대로 두었다. 저장소는 `x=1` 1271곳, `x = 1` 1942곳으로 갈려 있었고
  다수인 쪽이자 대입과 같은 모양을 골랐다).
- 속성(`#[...]`) 안의 `=`는 쓴 그대로 둔다. 저장소의 속성 809곳이 전부 `#[bind='x']`처럼 붙여 쓴다
  (2026-11-12 사용자 결정). 속성 안에 중첩된 괄호도 속성으로 본다.
- 이름 있는 인자는 `name: value`라 `=`가 없다.
- gofmt와 달리 정렬은 하지 않는다. 손으로 맞춘 열(`base   = none`)은 한 칸으로 줄어든다.
  줄 끝 주석 앞의 간격만 쓴 그대로 둔다.

## Pros vs Cons

Pros

- 호출 `foo(a, b)`와 초기화 `Vec2{x=1, y=2}`가 같은 규칙을 따라 읽는 방법이 하나다.
- 기존 코드의 절대다수와 같아서 포맷 적용 시 diff가 작다.
- 들여쓰기 언어라 중괄호가 블록에 쓰이지 않는다. Rust처럼 블록과 모양을 맞출 이유가 없다.

Cons

- JavaScript · Rust에 익숙하면 `Bar{x: 1}`류가 빽빽해 보인다.
- 타입 없는 리터럴 `{x=1, y=2}`도 같은 규칙이라 JavaScript 객체와 가장 달라 보이는 지점이 된다.
- `{`와 `}`는 안쪽을 붙이고 `=`는 띄우므로 `Vec2{x = 1}`은 Go(`P{X: 1}`)보다 Zig(`P{ .x = 1 }`)에 가까운 밀도가 된다.
- 값 출력(`print(Point{x=1, y=2})` → `Point{x=1, y=2}`)은 런타임 형식이라 포매터의 모양과 다르다.

## 남은 것

- 없음. 2026-11-12에 둘 다 정했다: 리터럴 필드의 `=`는 띄우는 쪽으로 통일(위 결정), 줄 끝 주석과 필드 열의
  정렬은 도구가 맡지 않는다(이름 하나를 바꾸면 이웃 줄까지 diff에 잡히고 폭이 다른 글자에서 열이 어긋난다).
- 저장소의 `.cy` 파일은 일괄로 다시 포맷하지 않았다. 규칙을 바꾸기 전에도 475개 중 312개가 `cyber fmt --check`에
  걸리는 상태였다(바꾼 뒤 355개).
