# 모듈 수준 연산자 함수: 양쪽 피연산자 조회 (2026-11-25)

## 배경

이항 연산자는 왼쪽 피연산자 타입의 메서드만 찾았다. `v * 2.0`은 `fn (&Vec2) `*`(s float)`로 되지만 `2.0 * v`는 왼쪽이
`float`라 'Expected `float`, found `Vec2`.' 오류였다. 모듈 수준에 `` fn `*`(s float, v Vec2) ``를 선언해도 연산자 식은 그것을
보지 않았다. Julia 검토(`docs/study/11-design-principles-review.md` 3.4 B의 2)에서 짚은 것이다.

## 결정 (사용자, 2026-11-25: B의 2 "자유 함수 꼴로 넣기")

1. `a op b`는 먼저 `a` 타입의 메서드 `op`를 찾는다(전과 같다). 없으면 `a` 타입을 선언한 모듈의 모듈 수준 함수 `op`, 그다음
   `b` 타입을 선언한 모듈의 것을 찾는다. 두 모듈에 다 있으면 오른쪽 타입을 받는 오버로드가 있는 쪽이 먼저다(`takesRight`).
2. 왼쪽이 수(`int` · `float` 등)이고 오른쪽이 수가 아니면 내장 연산 대신 오른쪽 타입 모듈의 함수를 찾는다. 왼쪽이 수 리터럴이면
   리터럴은 보통 호출 인자처럼 매개변수 타입을 따른다(`2 * v`가 `fn `*`(s float, v Vec2)`를 부른다).
3. 대상은 산술 · 비트 연산자(`+ - * / % ** && || ~ << >>`)다. 비교(`< <= > >=`)는 왼쪽 타입의 메서드로만 둔다. 모듈 수준에
   선언하면 오류다. `==`는 원래 규칙(core `@eq`)대로다.
4. 모듈 수준 연산자 함수는 매개변수가 둘이고, 그중 하나(빌림이면 그 안의 타입)가 같은 모듈에서 선언한 타입이어야 한다. 아니면
   선언 자리에서 오류다(Rust의 orphan rule과 같은 뜻). 조회가 피연산자 타입의 모듈만 보므로 다른 곳의 정의는 불리지 않는다.
   infer 매개변수(`s %T`)가 있으면 검사하지 않는다.
5. 반사 메서드(Python `__rmul__`)는 들이지 않는다. 새 개념 없이 기존 자유 함수 오버로드로 된다.

## 구현

- `src/sema_expr.zig` `semaBinExpr`의 산술 · 비트 갈래: 수 리터럴 · 정수 · float 왼쪽에서 오른쪽이 수가 아니면 `semaFreeOp`,
  사용자 타입 왼쪽에서 메서드가 없으면 `hasFreeOp` 뒤 `semaFreeOp`. 두 피연산자는 receiver 인자로 넘겨 `&T` 매개변수가 자동
  빌림을 받는다. 리터럴 왼쪽은 보통 인자(`Argument.init`)라 매개변수 타입으로 맞춘다.
- `freeOpSym`: 타입 심볼의 root chunk 모듈에서 연산자 이름을 찾는다. core(`builtins_chunk`)와 수 타입은 보지 않는다.
- `src/module.zig` `checkFreeOperatorFunc`(`resolveUserFunc`에서): 위 3 · 4의 선언 검사.

## 하지 않은 것

- 비교 연산자의 양쪽 조회. `2 < v` 같은 식을 쓸 일이 드물고, 비교는 `==` · 정렬 규칙과 묶여 있다.
- 메서드와 모듈 수준 함수 사이의 오버로드 해석. 왼쪽 타입에 메서드 `op`가 있으면 그것만 본다(오른쪽 타입이 맞지 않아도).
- REPL 세션에서 앞 입력의 타입에 뒤 입력이 연산자 함수를 선언하는 것: 조회가 타입을 선언한 입력의 모듈만 보고, 선언 검사도
  같은 입력의 타입만 인정해 오류다.
- 직접 호출 `` `*`(3.0, v) ``는 core의 포인터 타입 이름 `*`로 해석돼 되지 않는다(전과 같다).
