# Cyber 0.4.20

릴리스일 2026-11-25. 태그 `0.4.20` → `b407c7b9`, 빌드 `build-1165-b407c7b`.

0.4.19 이후의 릴리스다. 산술과 비교에서 정수와 float를 어느 순서로든 섞고(`i * f`), 외부 프로그램을 값으로 다루는 `os.cmd`를 넣고,
REPL에 조회 명령(`.doc` · `.which` · `.bc` · `.help`)을 더했다. REPL 세션이 `os` · `cli` · 파일 모듈을 가져오고, 세션의 뒤 입력이 앞 입력의
타입에 메서드를 선언한다. 컴파일 타임 수 연산이 런타임과 같은 값을 내고, 템플릿 오버로드가 infer 파라미터 타입의 꼴로 갈린다.
호스트 프로세스를 끝내던 결함 여럿(F-199 · F-203 · F-204 · F-205 · F-206 · F-207)을 고쳤다. 매뉴얼의 Planned 항목을 정리하고
`os.open_lib`을 지웠다.

## 호환성

0.4.19에서 돌던 스크립트의 동작이 이번 버전에서 달라지는 변경이다. 자세한 규칙과 예는 아래 각 절에 있다.

새로 컴파일 오류가 되는 코드:

- `os.open_lib`, `os.DynLib`('Can not find the symbol `open_lib` in `os`.'). 0.4.19에서도 호출하면 'TODO' panic이었다. C 라이브러리는 `#c.bind_lib(path)`.
- 왼쪽이 float이고 오른쪽이 수가 아닌 산술(`f + 'abc'`, `f * true`). 0.4.19는 오른쪽 비트를 float로 읽은 값을 냈다(F-196).
- `g += f`(`g f32`, `f float`): 'Expected type `f32`, got `float`.'. 0.4.19는 아무 일도 하지 않았다(F-196).
- `symbol` · `error`를 float 자리에 쓰는 것(`2.5 * symbol.a`, `var f float = symbol.a`). 0.4.19는 수로 바꿨다(F-201).
- `const z = k / 0`, `const z = k % 0`: 'Division by zero.'. 0.4.19는 호스트 panic이었다(F-206).

조용히 달라지는 동작:

- `f32 op float`의 결과: `var g f32 = 1.5`, `f := 2.5`에서 `g * f`가 `0.0`이 아니라 `3.75`(`float`)다(F-196).
- `const r = 2.5 * k`(정수 상수 `k`)가 비정규 수 대신 `7.5` 꼴의 맞는 값이다(F-197).
- REPL에서 줄 맨 앞의 `.help`, `.doc ...`, `.which ...`, `.bc ...`는 명령이다. 0.4.19에서는 컴파일 오류였다.
- 세션의 eval마다 다른 uri를 주는 호스트는 앞 eval의 `-` 심볼이 뒤 eval에서 보인다(매뉴얼이 적은 대로).

전에는 오류(또는 호스트 종료)였고 이제 되는 코드:

- `i * f`, `i < 7.5`, `i == 7.0`, `i8 < int`: 정수와 float, 폭이 다른 정수가 어느 순서로든 섞인다.
- `os.cmd({'ls'}).pipe(os.cmd({'wc', '-l'})).read()`.
- REPL에서 `use os`, 앞 입력의 타입에 메서드 선언(`fn (&V) twice()`), `use math` 뒤 `use os`, `libc.printf(s, 7)`.
- `const w = 1.5 + 2.0`, `const z = a * 2`(`a i32`), `const r = k % 3`, `const e = error.Foo` 등 컴파일 타임 수 연산과 `error` 상수.
- `fn f(x ?%T)`와 `fn f(x []%T)` 같은 템플릿 오버로드, 타입 인자의 오버로드(`make(int, 1)`), 컴파일 타임 호출의 오버로드.

## 매뉴얼의 Planned 항목 정리와 `os.open_lib` 삭제 (2026-11-24)

C 백엔드를 지운 뒤 `docs/docs.md`에 남은 흔적과 `Planned Feature` 표시를 검토했다. 남길 계획과 뺄 계획은 사용자가 정했다.
결정과 항목별 대안은 `docs/decisions/project_planned_features.md`.

- 호환성: `os.open_lib`과 `os.DynLib`이 없어졌다. 전에도 호출하면 'TODO' panic이었다. 이제 'Can not find the symbol `open_lib` in `os`.'
  컴파일 오류다. C 라이브러리는 `#c.bind_lib(path)`로 묶는다.
- 매뉴얼에 남은 계획: optional chaining, named parameters, `error` set 타입, 더 많은 `Sendable` 타입, destructure import.
  destructure import의 꼴은 `use { cos, pi } from 'math'`로 바꿨다.
- 계획에서 뺀 것: `fmt`의 이름 있는 자리표시자, line-join 리터럴, 가변 `Str`, `?else` 블록의 `break 값`, `+..` 슬라이스, 내용 없는
  호출 절 둘, `defer`, 반환값 구조 분해, 타입 템플릿의 제네릭 타입, 내장 `clone`, weak reference, `@check_cycles`, 할당마다 고르는
  allocator, `error` payload, Future chain, 스레드 사이 공유 메모리 · 채널, 타입이 다른 future의 `await`, 스레드 상태 조회,
  언어 차원의 SIMD, sandbox 모드. 매뉴얼에는 대신 쓰는 방법이 남는다(Cloning은 `clone` 메서드, Back references는 인덱스 · 키,
  Errors는 `Diag`, 타입 템플릿은 `MyContainer[%T]`).
- C 백엔드의 흔적: 매뉴얼 소개의 "Compilation ahead-of-time to C"와 `extern`의 "static or runtime binding"을 고쳤다.
  `MEMORY.md`, `project_direction.md`, `project_coroutines.md`, `docs/study`의 해당 줄에 삭제 사실을 덧붙였다.

## 수 피연산자의 대칭 변환 (2026-11-24)

산술 연산자와 비교에서 정수와 float를 어느 순서로 써도 된다. 결정과 구현은 `docs/decisions/project_number_operands.md`,
계기는 Julia 검토(`docs/study/11-design-principles-review.md` 3.4 B).

- `i * f`가 `f * i`와 같다. 전에는 'Expected `int`, found `float`.' 오류였다. `+ - * / % **`와 `< <= > >= == !=`에 적용된다.
  정수가 float 피연산자의 타입으로 변환되고 결과는 float다. `i * 2.5`, `i < 7.5`, `i == 7.0`도 된다.
- `f32`와 `float`를 섞으면 어느 순서든 `float`다. 비교에서는 폭이 다른 정수도 왼쪽이 넓혀진다(`i8 < int`).
- 결과는 정수로 되돌아가지 않는다. `i += f`, `var n int = i * f`는 'Expected type `int`, got `float`.' 오류다. `int(i * f)`로 쓴다.
- 두 정수의 나눗셈은 그대로 정수 나눗셈이다(`i / 2`). 비트 연산자는 정수만 받는다(`i && f`는 전과 같은 오류).
- 컴파일 타임 평가도 같은 규칙이다. `const r = k * 2.5`가 된다. float의 다른 컴파일 타임 연산은 아래 "컴파일 타임 수 연산" 절에서 넣었다.
- 호환성(전에 틀린 값을 내던 코드가 오류나 다른 값이 된다):
  - `f + 'abc'`, `f * true`처럼 왼쪽이 float이고 오른쪽이 수가 아닌 산술이 컴파일 오류가 됐다('Expected `float`, found `str`.').
    전에는 오른쪽의 비트를 float로 읽은 값이 나왔다(F-196).
  - `f32 op float`의 결과가 바뀐다. `var g f32 = 1.5`, `f := 2.5`에서 `g * f`는 `0.0`이 아니라 `3.75`(`float`)다.
    `g += f`는 아무 일도 하지 않던 것이 'Expected type `f32`, got `float`.' 오류가 됐다(F-196).
  - `const r = 2.5 * k`(정수 상수 `k`)가 비정규 수 대신 맞는 값을 낸다(F-197).
- 매뉴얼: Arithmetic operators · Comparison operators · Implicit casts · Inline evaluation 절. 에이전트 안내의 정수 · float 항목과
  오류 문구 둘.
- 하지 않은 것: 사용자 타입 연산자의 양쪽 조회(`2.0 * v`). 컴파일 타임의 float 연산 확장은 뒤 절에서 했다.
- 확인: 14단계 검증에서 1~8 · 13 · 14단계 rc=0. 9~12단계(wasm 실행)는 세션 컨테이너에 `wasmtime` 실행 파일이 없어 Python `wasmtime`
  패키지로 같은 wasm 파일을 돌렸고 넷 다 통과했다(behavior 820개, cli 13개, lib 181개, trace 15개).

## `os.cmd`: 명령을 값으로 (2026-11-24)

외부 프로그램을 파이프 · 작업 디렉터리 · 환경 변수 · stdin과 함께 돌린다. shell을 거치지 않는다. 결정과 구현은
`docs/decisions/project_os_cmd.md`, 계기는 Julia 검토(`docs/study/11-design-principles-review.md` 3.4 A).

- `os.cmd(args)`가 `Cmd` 값을 만든다. `pipe(next)` · `dir(path)` · `env(name, value)` · `stdin(text)`는 새 `Cmd`를 돌려주고,
  `run()` · `read()` · `run_status()`를 부를 때 시작한다.
  - `run() -> !void`: 출력이 이 프로세스의 stdout · stderr로 간다.
  - `read() -> !str`: 마지막 프로그램의 stdout.
  - `run_status() -> !ExecResult`: stdout, 모든 프로그램의 stderr, 종료 코드. 0이 아닌 코드가 오류가 아니다.
- 실패한 종료는 `run` · `read`에서 `error.ExitStatus`다. 파이프라인은 어느 프로그램이든 실패하면 실패이고, 다음 프로그램이 입력을
  닫아 끝난 프로그램(`yes | head -1`의 `yes`)은 성공이다. `run_status`의 `code`는 실패한 것 가운데 마지막 프로그램의 코드, 신호는
  128 + 신호 번호다.
- 시작하지 못한 프로그램은 오류 값이다: `error.NotFound` · `error.PermissionDenied` · `error.InvalidArgument` 등 OS 오류의 표준 이름.
- 잡는 출력은 stdout · stderr 각각 10 MiB까지(`error.TooBig`), 파이프라인은 16개까지다.
- 호환성:
  - `os.exec`와 `os.cmd`의 자식이 `os.set_env`로 정한 변수를 받는다. 전에는 받지 못했다(F-198). 변수를 정해 놓고 자식에게는
    안 보이기를 기대한 스크립트가 있다면 달라진다.
  - `os.exec`는 그대로다(반환 타입, 시작 실패의 panic). 문서 주석의 "Runs a shell command"만 고쳤다. shell은 전에도 거치지 않았다.
- 매뉴얼: Builtin modules의 Running programs 절. 에이전트 안내의 `os` 항목. `docs/api.json`.
- 확인 못 한 것: macOS · Windows에서의 실행. 세 대상 모두 교차 컴파일은 된다. 테스트는 POSIX 프로그램을 써서 Windows에서는
  본문을 건너뛴다.
- 하지 않은 것: 파일 리다이렉션, 줄 단위 스트리밍, 실행 중 중단 · 시간 제한.
- 확인: 14단계 검증 rc=0(9~12단계는 Python `wasmtime` 패키지로 만든 `wasmtime` 대역으로 실행).

## REPL 조회 명령 `.doc` · `.which` · `.bc` (2026-11-24)

REPL에서 문서, 호출이 고르는 함수, 바이트코드를 본다. 결정과 구현은 `docs/decisions/project_repl_commands.md`, 계기는 Julia
검토(`docs/study/11-design-principles-review.md` 3.4 E).

- `.help`: 명령 목록. 시작 줄이 `Commands: .exit, .help`가 됐다.
- `.doc [topic]`: `cyber doc`이 찍는 것(`.doc optionals`, `.doc --list`, `.doc --api os`). CLI의 REPL에만 있다.
- `.which <expr>`: 식을 세션에 대해 컴파일만 하고, 가장 바깥 호출이 고른 함수의 선언 첫 줄 · 템플릿 인스턴스 · 오버로드 수 ·
  선언 위치 · `--|` 문서 주석을 보여 준다. 호출이 없으면 끝의 이름이 무엇인지. 아무것도 실행하지 않는다.
- `.bc <function>`: 그 이름의 컴파일된 함수(오버로드, 템플릿 인스턴스 전부)의 바이트코드.
- 명령은 입력이 시작하는 자리에서만 읽는다. 블록 안에서는 전처럼 코드의 한 줄이다.
- 스크립트용: `cy.VM.which(code) -> str`, `cy.VM.bytecode(name) -> str`, `cy.repl(read_line, doc)` 오버로드, `cli.repl_doc(query)`.
- 호환성: 줄 맨 앞의 `.help`, `.doc ...`, `.which ...`, `.bc ...`가 REPL에서 코드로 평가되지 않는다. 전에는 컴파일 오류였다.
- 매뉴얼: REPL 장의 REPL commands 절. `docs/api.json`.
- 작업 중 찾은 기존 결함: 세션에서 앞 입력의 타입에 메서드를 선언하면 호스트가 죽는다(F-199, 아래 "세션의 뒤 입력이 앞 입력의
  타입에 메서드를 선언한다"에서 고침), CLI의 REPL에서 `use os`가 실패한다(F-200, 아래 "REPL이 CLI의 모듈을 가져온다"에서 고침).
- 확인: 14단계 검증 rc=0(9~12단계는 Python `wasmtime` 패키지로 만든 `wasmtime` 대역으로 실행).

## PR #12 리뷰에서 나온 수정 (2026-11-24)

위 세 절(수 피연산자, `os.cmd`, REPL 명령)을 묶은 PR의 코드 리뷰 10건. 릴리스 전의 변경이라 사용자에게는 위 절들의 최종 동작만 보인다.

- 수 피연산자: 왼쪽 변환을 수 타입으로 좁혔다. `symbol` · `error`(distinct raw)는 변환하지 않고, 비교에서 부호 있는 정수는 raw
  타입으로 변환하지 않는다(`i8 < r64`는 타입 오류). 처음 꼴에서는 `-1 < r64(5)`가 `false`, `symbol.a * 2.5`가 `125.0`이었다.
- 호환성: `symbol` · `error`가 float 자리에서 수로 변환되지 않는다(F-201). 0.4.19에서는 `2.5 * symbol.a`가 `125.0`,
  `var f float = symbol.a`가 통과했다. 이제 'Expected `float`, found `symbol`.' 타입 오류다.
- `os.cmd`: 입력 글이 있는 명령이 출력 한도를 넘는 등 시작 뒤에 실패하면 멈추던 것을 고쳤다. Windows에서는 환경 map을 만들지
  않아 `os.exec`의 Windows 경로가 0.4.19와 같다. `a.pipe(b)`가 `b`의 입력 글을 쓰지 않는다고 문서에 적었다.
- `os.cmd`: `yes | head -1` 꼴의 파이프라인이 `error.ExitStatus`가 되는 길 둘을 막았다(PR의 macOS CI에서 드러남). 이 프로세스가
  `SIGPIPE`를 무시하면 자식도 물려받으므로, 파이프라인을 시작하기 전에 무시를 아무 일도 하지 않는 핸들러로 바꾼다. 그리고
  입력 글을 쓰는 스레드가 macOS에서 프로세스 전체의 신호 mask를 바꾸던 것을 고쳤다(`sigprocmask` 대신 그 파이프의
  `F_SETNOSIGPIPE`, 다른 POSIX는 `pthread_sigmask`).
- `.which`: 선언 위치를 uri가 아니라 청크로 찾는다. 세션의 뒤 eval에서 선언한 함수의 줄 번호가 맞다.
- 문서: 컴파일 타임의 `==` · `!=`는 정수와 float를 섞지 못한다고 고쳤다. `semaRightOperand`의 문서 주석 자리.
- 테스트: `core/number_signed_raw_compare_error.cy` · `symbol_op_float_error.cy` · `float_op_symbol_error.cy` ·
  `error_eq_float_error.cy`, `modules/os_cmd.cy`(입력 중의 `TooBig`, 파이프 뒤 명령의 입력, `pwd -P`), `modules/cy.cy`(뒤 eval의 위치).

## 세션의 뒤 입력이 앞 입력의 타입에 메서드를 선언한다 (2026-11-24, F-199 · F-202)

`persist_main` 세션(REPL, `cy.VM`, 임베딩 호스트)에서 앞 입력이 선언한 타입에 뒤 입력이 메서드나 타입 함수를 선언하면 호스트
프로세스가 죽었다(`module.reserveFunc`의 'attempt to use null value'). 이제 같은 소스에서 선언한 것처럼 동작한다. 결정과 구현은
`docs/decisions/project_session_methods.md`.

- 받는 선언: 메서드(`fn (&V) twice()`), 타입 함수(`fn V :: make()`), 타입의 상수 · 함수 템플릿, 템플릿 타입의 멤버
  (`fn (&Box[]) get() -> T`). struct · enum · choice 타입.
- 매개변수 타입이 다른 같은 이름은 오버로드로 더한다. 같은 시그니처는 한 소스에서와 같은 오류다
  ('`twice` has already been declared with the same function signature.'). 메서드를 바꾸려면 타입을 다시 선언한다.
- 템플릿 타입: 새 메서드와 새 오버로드가 앞 입력이 만든 인스턴스(`Box[int]`)에도 생긴다.
- 실패한 입력과 `cl_vm_validate` · `.which`는 타입에 아무것도 남기지 않는다. 같은 선언을 다시 넣을 수 있다.
- 새 컴파일 오류(전에는 모두 호스트 panic):
  - 'Can not declare `@deinit` for `V` after the input that declares `V`. ...': `@deinit` · `@copy` · `@clone` · `@send`는 타입과
    같은 입력에 선언한다. 앞서 컴파일된 코드가 그것 없이 값을 없애고 복사하고 보내기 때문이다.
  - 'Can not declare `twice` for `V`: `V` belongs to another module. ...': 다른 모듈 타입의 `use` 별칭, 모듈 이름. 한 소스에서도 같다.
  - 'Can not declare `bar` for `foo`: `foo` is not a type. ...': 부모가 함수 · 전역 · 상수. 한 소스에서도 같다.
- `cl_vm_validate`와 `.which`가 eval이 받는 소스를 거절하던 것을 고쳤다(F-202): 세션의 uri가 `main`이 아니면 앞 eval 타입의 `-`
  필드를 읽는 소스가 'Can not access the private field'였다. `persist_main` 컴파일의 main 청크들은 uri와 상관없이 한 모듈이다.
- 호환성: 전에 컴파일되던 소스 중 달라지는 것은 없다(위의 경우는 모두 panic이었다). 세션의 eval마다 다른 uri를 주는 호스트는
  앞 eval의 `-` 심볼이 뒤 eval에서 보이게 된다(매뉴얼이 적은 대로).
- 한계: CLI의 REPL은 타입 블록이 한 입력이라 `@deinit` 등 네 메서드를 가진 타입은 여전히 REPL에서 선언할 수 없다(스크립트와
  호스트는 한 소스에 함께 넣는다). 템플릿 인스턴스는 전개할 때 찾은 것을 갖고 있다(`meta.has_decl(T, 'twice')`로 갈래를 고른 인스턴스는 뒤에 생긴 `twice`를
  보지 못한다). 템플릿 메서드의 중복 선언은 어떤 인스턴스도 그 이름을 쓰지 않았으면 다음 사용에서 드러난다.
- 매뉴얼: Methods 절(모듈 규칙), REPL 장, `cl_vm_validate` 절, 가시성 절.
- 확인: 14단계 검증 rc=0(9~12단계는 Python `wasmtime` 패키지로 만든 `wasmtime` 대역으로 실행). 그 뒤 매뉴얼의 REPL 문장 둘만
  고쳤다.

## REPL이 CLI의 모듈을 가져온다 (2026-11-24)

CLI의 REPL에서 `use os`가 'Failed to load module: os'였다(F-200). 세션의 VM이 `cy.VM()`의 격리된 VM이라 CLI의 loader가 없었다.
결정과 검토한 안은 `docs/decisions/project_repl_modules.md`.

- REPL 세션이 `cyber`로 돌린 스크립트가 가져오는 것을 가져온다: `os` · `cli` · `libc`, 파일(`use m 'm.cy'`, 작업 디렉터리 기준),
  URL. 전에는 라이브러리의 모듈(`math` · `json` 등)만 됐다.
- `cy.VM()` · `cy.eval` · `cy.repl(read_line)` · `cy.repl(read_line, doc)`은 그대로 격리다. 호스트의 resolver · loader를 받지 않는다.
  `cy.repl`을 직접 부르는 호스트의 모듈 정책은 바뀌지 않는다.
- 새 함수:
  - `cli.new_vm() -> cy.VM`: CLI가 가져오는 것을 가져오는 VM. CLI 스크립트에서 `os`를 쓰는 eval은 `cli.new_vm().eval(...)`.
  - `cy.REPL.new(vm VM)`: 부르는 쪽이 만든 VM에서 세션을 돈다. `REPL.new()`는 `REPL.new(VM())`과 같다.
  - `cy.REPL.run(read_line)`: 소개 줄을 찍고 `.exit`까지 읽고 평가한다.
- `cli.repl()`의 문서 주석이 'isolated REPL session'에서 바뀌었다. 세션은 여전히 자기 VM에서 돈다(값 · 전역 · 타입이 따로이고
  panic은 세션만 리셋한다).
- 함께 고친 것(F-203, 치명): `persist_main` 세션에서 extern 함수가 호스트를 끝내던 둘. `cy.VM()` 세션과 임베딩 호스트의 세션도
  같은 길이었다.
  - 앞 eval이 extern 함수를 묶은 뒤 뒤 eval이 extern 함수가 있는 모듈을 올리면 `'thread_ret' defined twice` 뒤 abort했다
    (REPL: `use math` 뒤 `use os`). 바인딩마다 새 TCC state를 쓰고 묶인 함수는 다시 만들지 않는다.
  - 앞 eval이 선언한 extern 함수를 뒤 eval이 부르면 세그폴트였다(REPL: `use libc` 뒤 다음 입력의 `libc.getenv(s)`). 뒤 eval의
    호출 자리에도 주소를 채운다.
- 함께 고친 것: CLI의 loader가 파일 · URL 모듈의 소스를 불러오는 VM의 allocator로 읽는다(전에는 CLI의 allocator. CLI의 VM에서는
  둘이 같아 드러나지 않았다).
- 알려진 한계:
  - 가변 인자 extern 함수에 `int`를 넘기면 호스트가 abort했다(F-204). 아래 절에서 고쳤다.
  - REPL에서도 `os.cwd()`는 `os.cwd()!`로 써야 한다('Expected to handle the error case for `!str`.').
  - F-199는 그대로다.
- 매뉴얼: REPL 장(세션의 import), Runtime execution 절(`cy.eval`의 격리, `cli.new_vm()`, `cy.REPL.new(vm)`), libcyber 장의 resolver
  절(`cy.VM()` · `cy.repl`도 격리임). `docs/api.json`.
- 테스트: behavior `modules/cy.cy`(격리 계약, `REPL.new(vm)`, `REPL.run`), `modules/cli.cy`, `modules/cli_os.cy`, `ffi/session.cy`.
  `src/tools/verify.sh`에 15단계 `15-repl-stdin`(빌드한 `cyber`의 REPL에 줄을 파이프로 넣는다)을 더했다.
- 확인: 15단계 검증에서 9단계만 실패했다(rc=1, 나머지 rc=0). wasm에서 없는 파일의 오류를 resolver가 아니라 loader가 내어
  `modules/cli.cy`의 문구 단언이 맞지 않았다. 단언을 경로만 보게 고친 뒤 9단계를 다시 돌려 rc=0(behavior 821개), 같은 파일을
  Debug · ReleaseSafe CLI로도 다시 돌렸다. 9~12단계는 세션 컨테이너에 `wasmtime` 실행 파일이 없어 Python `wasmtime` 패키지로 돌렸다.

## 가변 인자 extern 함수의 `int` · `float` 인자 (2026-11-24, F-204)

- 가변 인자 extern 함수에 `int`를 넘기면 호스트가 끝나던 것을 고쳤다(전부터 있던 결함). `libc.printf(s, 7)`이
  `'Int_0' undeclared` 뒤 'Failed to compile c source.'로 abort했다. 파일로 돌려도, 세션에서도 같았다. `float` · `f32` · `r16`도
  같은 길이였고(`'Float_0' undeclared`), C 이름이 미리 정해진 `i8` · `i16` · `i32` · `r32` · `r64` · `bool`과 포인터만 됐다.
- 원인: 호출마다 만드는 변형 함수(`vm_extern_variant`)의 C 래퍼가 원래 선언(`args c.variadic`)의 매개변수 타입만 선언하고,
  변형이 받은 인자의 타입은 선언하지 않았다. 이제 `cgen.genVmToExternFunc`가 자기 매개변수 · 반환 타입을 선언한다.
- C 함수에는 C의 기본 인자 승격이 그대로 적용된다(`f32`는 `double`로, `i8`은 `int`로). `int`는 64비트이므로 형식 문자열은
  `%lld`(또는 `%ld`)로 쓴다.
- 테스트: behavior `ffi/variadic.cy`(`int` · `i8` · `i16` · `i32` · `float` · `f32` · `r64` · `r32` · `r16` · `bool` · 포인터).

## 같은 VM의 eval마다 남는 메모리를 줄였다 (2026-11-24)

- 같은 VM에서 eval을 거듭하면 eval마다 메모리가 자랐다. 각 eval의 main 청크가 VM이 끝날 때까지 남고, 그 청크가 쓰지 않는
  명령 버퍼 4 KB와 sema · 코드 생성 작업 스택의 자리를 가졌다. 이제 코드를 다 만든 청크는 그 몫을 돌려준다.
- `x := 1`을 거듭하면 eval마다 약 15.2 KB에서 9.6 KB로 줄었다(macOS Debug). 남는 몫은 앞 eval의 함수 · 타입을 뒤 eval이 쓸 수
  있어 남기는 것(바이트코드, AST · IR, 심볼, 디버그 표)이고 소스 크기에 비례한다. 오래 도는 세션 호스트는 VM을 주기적으로
  새로 만든다.
- 결정 `docs/decisions/project_memory_limit.md` "eval마다 남는 메모리", 테스트 lib `A chunk whose code is done keeps no room it
  does not use.`

## 선언 해석 중의 `type.info` (2026-11-24, F-205)

- 선언이 이름으로 부르는 템플릿 안의 `type.info`가 호스트를 끝내던 것을 고쳤다(전부터 있던 결함). 예: 필드 타입이
  `x StructOf[P]`이고 `StructOf`가 `type.info(T).!struct`를 읽으면 panic 'No such field `name`.'이었다. 선언을 해석하는 동안에는
  `meta` 모듈의 정보 타입(`StructField` · `EnumCase` 등)이 아직 해석되지 않았는데, 그 타입으로 값을 만들었다. 이제 정보 타입을
  찾을 때 해석한다.
- `cyber src/builtins/cy.cy`(내장 모듈 소스를 main으로 실행)도 같은 panic이었다. 이제 'Host func `_parser_comments` failed to
  load.' 컴파일 오류다(내장 모듈의 호스트 함수는 그 모듈로 올릴 때만 묶인다).
- 테스트: behavior `meta/type_info_in_decl.cy`(struct · enum · choice).

## REPL에서 옮긴 변수의 오류 문구 (2026-11-24)

- REPL(`persist_main` 세션)에서 `b := move a` 뒤 다음 입력이 `a`를 쓰면 일반 'Undeclared variable `a`.'이었다. 이제
  '`a` was moved by an earlier input. Declare it again with `a := ...` to use the name.'이다. 같은 입력 안에서 옮긴 뒤 쓰면
  전처럼 '`a` was moved at L:C. ...'이다. 다시 선언하면(`a := ...`) 보통 변수로 돌아온다. panic으로 지역이 모두 버려지면
  옮긴 이름의 기록도 버린다.
- 매뉴얼: REPL 장. 테스트: lib `A main local that an earlier eval moved is named as moved.`(`src/lib_test/session.zig`).

## 계산한 크기 안의 infer 파라미터 (2026-11-24)

- 함수 타입 매개변수의 계산한 크기 안에 쓴 infer 파라미터(`f fn(T) -> [%N + 1]T`)를 시그니처가 infer 파라미터로 찾지 않았다.
  이름 있는 함수를 넘기면 'Can not infer a template parameter from the argument for `f`. Declare it as its own parameter (`%T
  type`) ...'으로 엉뚱한 이름을 말했고, 추론 람다를 넘기면 'Can not infer function type. ...'이었다. 이제 둘 다 같은 별칭
  (`type V2[const N int, T Any] = fn(T) -> [N + 1]T`)의 경우처럼 'Can not infer the template parameter `N` from the argument for
  `f`. ...'이다. 인자의 타입에서 `N`을 거꾸로 풀지는 않는다(0.4.19의 남은 한계는 문구만 고쳤다).
- 매뉴얼: 템플릿 파라미터 추론 절. 테스트: behavior `meta/infer_param_func_type_expr_error.cy`, `meta/infer_param_lambda_expr_error.cy`.

## 컴파일 타임 수 연산 (2026-11-24)

`const`와 컴파일 타임 본문(`#` 함수, `#{}`)의 수 연산이 런타임과 같은 값을 낸다. 결정과 구현은
`docs/decisions/project_number_operands.md` "컴파일 타임 수 연산".

- 호스트 panic 넷을 고쳤다(F-206 · F-207). `const z = k / 0` · `k % 0`, 가장 작은 `int`를 `-1`로 나누기, `1 << 70`, `symbol` 타입
  `const`를 읽는 식이 호스트를 끝냈다. 이제 정수의 `/` · `%` 0은 'Division by zero.' 컴파일 오류이고(런타임은 같은 문구의 panic),
  나머지는 런타임과 같은 값이다.
- 내장 수 타입(`Int[W]` · `Raw[W]` · `Float[W]`)의 `+ - * / % **`, `&& || ~ << >>`, `< <= > >=`가 모든 폭에서 된다. 전에는 타입마다
  몇 연산만 있어 'Unsupported inline eval: plus'였다(예: `const w = 1.5 + 2.0`, `const z = a * 2`(`a i32`), `const r = k % 3`).
  정수는 폭에서 래핑하고, `/`는 0 쪽으로 자르고, `>>`는 논리 시프트이고, 시프트 양은 아래 6비트를 쓴다. `Raw`에는 `**`가 없다.
- 폭이 다른 정수는 좁은 쪽이 넓혀진다. `const z = k * a`(`a i8`, `k int`)가 `int`다. 전에는 'Expected type `int`. Found `i8`.'였다.
  비교에서 부호 있는 정수는 raw 타입으로 바뀌지 않는다(`a < r`(`a i8`, `r r64`)는 런타임처럼 타입 오류).
- float의 `==` · `!=`, 정수와 float의 `==`(`const t = k == 7.0`)가 된다. 전에는 'Unsupported float.'와 타입 오류였다.
- 확인: behavior 테스트 `core/number_const_ops.cy`(같은 연산을 `const`와 런타임 변수로 계산해 비교), `core/number_const_div_zero_error.cy`.
- `error.Name`이 컴파일 타임 식이 됐다. `const e = error.Foo`, `const t = e == error.Foo`가 된다. 전에는 'Unsupported compile-time
  expression: `error_lit`' 오류였다.

## 템플릿 오버로드의 남은 한계 (2026-11-24)

0.4.19에서 남긴 템플릿 오버로드 한계 셋 가운데 둘을 고쳤다(`docs/releases/0.4.19.md` "남은 한계").

- infer 파라미터가 든 파라미터 타입의 꼴만 다른 템플릿 오버로드를 선언할 수 있다. `fn f(x ?%T)`, `fn f(x []%T)`, `fn f(x %T)`,
  `f fn(T) -> ?%U`와 `f fn(T) -> []%U`. 전에는 둘째 선언이 'already been declared with the same function signature'였다. infer
  파라미터의 이름만 다른 같은 꼴(`fn f(x []%T)`와 `fn f(y []%U)`)은 그대로 그 오류다. 둘 이상이 받을 수 있으면 먼저 선언된 것을
  쓴다(`f({1, 2})`는 `%T`가 먼저면 그쪽).
  구현: `module.resolveFunc`가 infer 자리표시 타입(`infer_t` · `dependent_t`)이 있는 템플릿 서명이면 `checkTemplateOverloadUnique`로
  파라미터 타입의 소스(공백 없이, infer 이름은 순서 번호로)를 비교한다. 서명이 같은 자리표시라 서명 맵으로는 가를 수 없다.
- 타입 인자(`make(int, 1)`)가 `make(x str, n int)` 오버로드를 만나면 'Compile-time symbol cannot be used here.'로 끝나던 것이
  다음 후보(`make(%T type, n int)`)로 넘어간다. 오버로드 매칭 중 런타임 인자 자리의 타입 심볼은 infer 오류다
  (`sema_expr.semaIdent2`).
- 컴파일 타임 호출(`const a = f(3)`)에서 템플릿 후보가 인자를 받지 못하면 다음 후보로 넘어간다. 전에는 그 후보의 오류
  ('Expected template `Slice`. Found `Int`.', 'Expected type `type`. Found `int`.')로 끝났다. `matchGenericFuncCt` ·
  `matchTemplateArgCt`가 런타임 경로처럼 `overloaded`를 받고, 모두 실패하면 가장 멀리 간 후보를 혼자 다시 맞춰 보고한다.
- 남은 것: 실패한 오버로드 후보에서 끝까지 검사된 타입 선언형 람다는 죽은 코드로 남는다(동작에는 영향 없음). 컴파일 타임 호출의
  `str` 인자는 `EvalStr`라 `fn f(x str)`에 맞지 않는다('Expected argument `str`, found `EvalStr`', 전부터).
- 확인: behavior 테스트 `meta/infer_param_overload_form.cy`, `meta/infer_param_overload_form_error.cy`.
