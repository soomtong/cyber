# Cyber 0.4.21

릴리스일 2026-11-25. 태그 `0.4.21` → `1cb14490`, 빌드 `build-1186-1cb1449`.

0.4.20 이후의 릴리스다. `os.cmd`에 시간 제한, 중단, 파일 리다이렉션을 넣고, `Cmd.start()`가 돌려주는 `os.Process`로 실행 중인 명령의
출력을 줄 단위로 읽는다. `for`가 실패할 수 있는 반복자(`next() -> !?T`)를 받고, 그 오류는 본문 뒤의 `else |err|:` 블록이 다룬다.
연산자를 모듈 수준 함수로 선언해 `2.0 * v`를 쓰고, 모호한 오버로드 호출은 컴파일 오류가 됐다. 임베딩 호스트를 위해
`cl_vm_interrupt`가 `os.cmd` · `os.exec`와 빈 `while:` 반복에 닿고(F-208), panic · 중단으로 쓸린 값의 호스트 자원을 정리하는
`cl_vm_add_cleanup`이 늘었다. 열린 파일 · 디렉터리가 panic 뒤에도 닫힌다(F-209 · F-210).

## 설치

```bash
curl -fsSL https://raw.githubusercontent.com/soomtong/cyber/master/install.sh | bash -s 0.4.21
cyber --version   # Cyber 0.4.21 build-<n>-<commit>
```

## 호환성

0.4.20에서 돌던 스크립트의 동작이 이번 버전에서 달라지는 변경이다. 자세한 규칙과 예는 아래 각 절에 있다.

새로 컴파일 오류가 되는 코드:

- 두 오버로드가 같이 맞고 어느 쪽도 더 구체적이지 않은 호출(`tag(none)`에 `fn tag(x ?str)` · `fn tag(x ?int)`): 'The call is
  ambiguous: ...'. 0.4.20은 먼저 선언한 쪽을 조용히 불렀다. `tag(?str(none))`처럼 타입을 밝힌다.
- 모듈 수준 연산자 함수 `` fn `*`(a A, b B) ``가 이 모듈의 타입을 받지 않는 것, 비교 연산자(`<` 등)를 모듈 수준에 선언하는 것.
- `next`가 `!?T`인 반복자의 `for`에 `else` 블록이 없는 것('The iterator can fail: ...'). 0.4.20에서는 'Expected `Option` type.'으로
  어차피 컴파일되지 않았다.

조용히 달라지는 동작:

- `os.exec`: 신호로 끝난 프로그램의 `code`가 -1에서 128 + 신호 번호(`kill -9`는 137)다. 시작하지 못한 프로그램의 panic 문구가
  'FileNotFound'에서 'error.NotFound'다.
- 임베딩: `cl_vm_interrupt`가 실행 중인 `os.cmd` · `os.exec`의 프로그램을 끝낸다. panic · 중단으로 끝난 eval의 `os.File` ·
  `os.Dir` 핸들이 닫힌다.

전에는 오류(또는 멈춤)였고 이제 되는 코드:

- `2.0 * v`, `2 * v`(`Vec2`의 모듈에 `` fn `*`(s float, v Vec2) ``가 있을 때).
- `os.cmd(...).timeout_ms(5000)`, `.stdout_file(path)` · `.stdout_append` · `.stderr_file` · `.stderr_append` · `.stdin_file`.
- `p := cmd.start()!` 뒤 `p.read_line()`, `for p.lines() |line|: ... else |err|: ...`, `p.wait()`, `p.kill()`.
- `while:` 아래 `pass`뿐인 반복을 `cl_vm_interrupt` · fuel로 멈춘다(0.4.20은 호스트가 영영 기다렸다).

임베딩 C API에 늘어난 것: `cl_thread_interrupted`, `cl_vm_add_cleanup`, `cl_vm_remove_cleanup`.

## 모듈 수준 연산자 함수: `2.0 * v`

왼쪽 피연산자 타입에 연산자 메서드가 없으면 두 피연산자 타입을 선언한 모듈의 모듈 수준 함수 `` fn `op`(a A, b B) ``를 찾는다.
왼쪽이 수인 `2.0 * v` · `2 * v`를 `Vec2` 쪽 모듈이 정의할 수 있다. 전에는 'Expected `float`, found `Vec2`.' 오류였다.

~~~cy
fn `*`(s float, v Vec2) -> Vec2:
    return {x=s * v.x, y=s * v.y}

d := 2.0 * a
e := 2 * a      -- 리터럴은 매개변수 타입을 따른다.
~~~

- 산술 · 비트 연산자만이다. 비교 연산자(`< <= > >=`)를 모듈 수준에 선언하면 'Declare `<` as a method of the left operand
  type. ...' 오류다.
- 모듈 수준 연산자 함수는 매개변수가 둘이고 그중 하나가 같은 모듈의 타입이어야 한다. 아니면 'The operator function `*` must take
  a type declared in this module, ...' 오류다(깨지는 변경이지만 core · std · 테스트에 해당하는 선언은 없었다).
- 결정 `docs/decisions/project_operator_lookup.md`, 매뉴얼 Operator methods 절.

## 모호한 오버로드 호출은 컴파일 오류 (깨지는 변경)

두 오버로드가 같이 맞고 어느 쪽도 더 구체적이지 않으면 컴파일 오류다. 전에는 먼저 선언한 쪽을 조용히 불렀다. 선언 순서가
호출의 뜻을 정하지 않는다(Julia 검토 3.4 C, F-21의 나머지 반).

~~~cy
fn tag(x ?str) -> str: return 'str'
fn tag(x ?int) -> str: return 'option int'

print(tag(none))
-- CompileError: The call is ambiguous: both `fn tag(?str) -> str` and `fn tag(?int) -> str` match, and neither is more
-- specific. Write `tag(?str(none))` or `tag(?int(none))`.
~~~

- "더 구체적"은 `T`가 `?T` · `!T`보다 좁은 것이다. 정확히 맞는 후보가 있으면 그것들끼리, 없으면 암시적 변환으로 맞는 후보끼리 본다.
- 모호하지 않은 것: 수 타입끼리만 다른 오버로드(`float(x)`에 `i32`), 문자열 리터럴 자리에서 `str`과 정수만 다른 오버로드
  (`s.index('\n')`, json `v['n']`. 한 글자 리터럴은 문자열이 먼저다).
- 인자가 이름 · 리터럴 · 멤버 접근인 호출만 본다(타입이 매개변수에 따라 달라지는 인자).
- core · std · 테스트 · 예제에서 걸린 곳은 이 경우를 시험하던 테스트 하나였다. 컴파일 시간 차이는 재지 못할 만큼 작았다.
- 결정 `docs/decisions/project_overload_exact_match.md` 끝 절.

## `cyber-lsp`: 컴파일되지 않을 정규식 · PEG 리터럴

`regex.compile` · `peg.compile`에 문자열 리터럴을 넘기면 `cyber-lsp`가 실행 전에 그 패턴을 컴파일해 보고, 실패하면 Error
진단을 낸다. 실행할 때 받을 `Diag`의 문구 그대로다.

~~~cy
bad := regex.compile('xa(?=b)')
-- error: `regex.compile` will fail: Look-ahead (`(?=...)`, `(?!...)`) is not supported: ...
~~~

- 이스케이프가 없는 리터럴은 오류가 난 글자를, 있으면 리터럴 전체를 가리킨다. 보간이 있는 문자열은 보지 않는다.
- 임베딩은 `cl_vm_symbol_hints`의 `CL_HINT_PATTERN_LITERAL`(5)로 리터럴의 자리를 받는다. 컴파일 타임 검증(Julia 검토 3.4 F)은
  평가기를 넓힐 때까지 미룬다. LSP 설계 문서 19절.

## `os.cmd`: 시간 제한, 중단, 파일 리다이렉션

`Cmd`에 메서드 일곱이 늘었다. 결정 `docs/decisions/project_os_cmd.md` "시간 제한 · 중단 · 파일 리다이렉션".

~~~cy
os.cmd({'make'}).stdout_file('build.log').stderr_append('errors.log').timeout_ms(60000).run()!
n := os.cmd({'wc', '-l'}).stdin_file('data.csv').read()!
~~~

- `timeout_ms(ms)`: 기한이 지나면 단계들을 끝내고(`SIGKILL`, `TerminateProcess`) `error.TimedOut`을 돌려준다. 단계가 스스로
  띄운 프로그램은 끝내지 않는다. `pipe`는 둘 중 짧은 기한을 쓴다. 0 이하는 실행할 때 `error.InvalidArgument`.
- `cl_vm_interrupt`가 실행 중인 명령에 닿는다. 전에는 명령이 끝날 때까지 VM이 멈추지 않았다. 이제 단계들을 끝내고 VM이 멈춘다.
- `stdin_file(path)`, `stdout_file(path)` · `stdout_append(path)`, `stderr_file(path)` · `stderr_append(path)`. 파일은 실행할 때
  어느 단계도 시작하기 전에 연다. 상대 경로는 `dir`이 아니라 이 프로세스의 작업 디렉터리 기준이다. 파일로 보낸 스트림은
  `run_status`의 결과에 없고, stdout을 파일로 보낸 명령의 `read`는 `error.InvalidArgument`다.
- 명령 실행마다 감시 스레드 하나가 붙는다(macOS ReleaseFast에서 `true` 한 번에 약 0.05ms).
- 임베딩: `cl_thread_interrupted(t)`가 늘었다. 오래 막히는 호스트 함수가 중단 요청을 보고 일찍 돌아오게 한다.

## 빈 본문의 조건 없는 `while:`을 멈출 수 있다 (F-208)

`while:` 아래 `pass`만 있는 반복은 `cl_vm_interrupt`로도 fuel로도 멈추지 않았다. 자기 자신으로 뛰는 `jmp`(오프셋 0)가 되는데 VM은
뒤로 뛰는 점프(오프셋 < 0)에서만 중단 요청을 봤다. 이제 오프셋 0도 검사점이다. `while true: pass`는 조건 검사로 다른 자리에
뛰어서 전에도 멈췄다.

## `os.cmd`: 도는 동안 줄 단위로 읽기 (`Cmd.start`, `os.Process`)

`Cmd.start()`가 명령을 시작하고 도는 중인 `os.Process`를 돌려준다. 마지막 단계의 stdout을 쓰이는 대로 읽는다.
결정 `docs/decisions/project_os_cmd.md` "줄 단위 스트리밍", 예제 `examples/stream_lines.cy` · `examples/commands.cy`.

~~~cy
p := os.cmd({'tail', '-f', 'app.log'}).timeout_ms(60000).start()!
while p.read_line()! |line|:
    if line.contains('ready'):
        break
p.kill()
code := p.wait_code()!
~~~

- `read_line() -> !?str`(줄바꿈 `\n` · `\r\n` 제외, 끝이면 `none`), `read_all() -> !str`, `wait() -> !void`(`run`과 같은 오류),
  `wait_code() -> !int`, `kill()`.
- `wait`는 읽지 않은 stdout을 읽어 버린다(가득 찬 파이프에 단계가 멈추지 않게).
- 값이 명령이 끝나기 전에 사라지면 프로그램들을 끝내고 회수한다. eval이 panic · 중단으로 끝나 `@deinit` 없이 쓸려도 같다.
- `timeout_ms`는 `start`부터 센다. stdout을 파일로 보낸 명령의 `start`는 `error.InvalidArgument`.
- `lines()`: `for p.lines() |line|: ... else |err|: ...`(아래 "실패할 수 있는 반복자").
- 임베딩: `cl_vm_add_cleanup(vm, fn, ctx)` · `cl_vm_remove_cleanup(vm, id)`가 늘었다. 스크립트 값이 대신하는 호스트 자원을
  eval이 panic · 중단으로 끝날 때와 VM을 해제할 때 정리한다.

## `for`: 실패할 수 있는 반복자와 `else |err|:` 블록

반복자의 `next`가 `!?T`를 돌려주면 `for`가 받는다. 오류가 나면 반복이 끝나고 본문 뒤의 `else` 블록이 돈다(`|err|`는 생략 가능).
결정 `docs/decisions/project_for_fallible_iter.md`.

~~~cy
for p.lines() |line|:
    print(line)
else |err|:
    print('stopped: %{err}')
~~~

- `else` 블록은 필수다. 빠지면 'The iterator can fail: `next` returns `!?str`. Handle its error with an `else |err|:` block after the
  body of `for`.' 컴파일 오류다. 전에는 'Expected `Option` type.'이었다.
- `next`가 `?T`인 반복 뒤의 `else` 블록은 'An `else` block of `for` handles the error of an iterator that can fail, ...' 오류다.
- `else` 블록 안의 `continue`는 'continue can not go on with an iterator that failed. ...' 오류다(실패한 반복자를 다시 부르지
  않는다). 블록은 끝에 닿아도 되고(반복 뒤로 간다), `break` · `return`도 된다.

## panic · 중단으로 쓸린 `os.File` · `os.Dir`가 핸들을 닫는다 (F-210)

eval이 panic · 중단으로 끝나면 지역의 `@deinit`이 돌지 않아, 열린 파일과 디렉터리의 핸들이 프로세스가 끝날 때까지 남았다.
`persist_main` 세션이나 임베딩 호스트에서는 eval마다 쌓였다. 이제 `open_file` · `create_file` · `open_dir`가 연 핸들은
`cl_vm_add_cleanup`으로 그때 닫힌다(VM 해제 때도). 표준 스트림(`os.stdin()` 등)은 닫지 않는다. 열고 닫기 2만 번에서 시간 차이는
잡음 수준(+0.4%)이었다.

함께 고친 것(F-209): Linux의 `os.resolve_path`가 경로를 풀려고 연 fd를 닫지 않았다(macOS 갈래는 닫았다).

## `os.exec`를 멈출 수 있다 (깨지는 변경 둘)

`os.exec`가 `os.cmd(args).run_status()` 위에서 돈다. `cl_vm_interrupt`가 실행 중인 프로그램을 끝내고 VM을 멈춘다(전에는 프로그램이
끝날 때까지 기다렸다). 반환 타입과 시작 실패의 panic은 그대로다.

- 신호로 끝난 프로그램의 `code`가 -1에서 128 + 신호 번호다(`kill -9`는 137). `run_status`와 같다.
- 시작하지 못한 프로그램의 panic 문구가 'FileNotFound'에서 'error.NotFound'다(OS 오류 표준 이름).
