# Cyber 0.4.5

릴리스일 2026-11-11. 태그 `0.4.5` → `TAGCOMMIT`, 빌드 `BUILDNO`.

0.4.4 이후의 안정성 수정과 임베딩 API 보강을 담았다. 비정상 입력을 대량으로 넣어 찾은 컴파일러 · 런타임 abort(F-81, F-88 ~
F-94)를 모두 오류나 panic으로 바꿨고, 좁은 정수 연산의 틀린 값(F-82 · F-84)을 고쳤다. 호스트를 위해 메모리 한도와 C 메모리 함수,
호스트 할당 실패의 오류 반환, 구조화된 컴파일 오류(`cl_vm_compile_error`)를 더했다. 언어 쪽에서는 `Array`가 복사할 수 없는
원소를 담고(F-26), 빌림 순회 `for a |&elem|`이 생겼다.

## 설치

```bash
curl -fsSL https://raw.githubusercontent.com/soomtong/cyber/master/install.sh | bash -s 0.4.5
cyber version   # Cyber 0.4.5 BUILDNO
```

## 호환성

0.4.4에서 컴파일되거나 돌던 스크립트 · 호스트 코드가 이번 버전에서 오류가 될 수 있는 변경이다. 자세한 내용은 아래 절과
`docs/docs.md`에 있다.

- 전역 초기화식이 부른 함수가 더 늦게 선언된 전역(또는 자기 자신)에 닿으면 컴파일 오류다. 모듈 사이의 전역 초기화 · 정리 순서도
  바뀌었다(가져온 모듈 먼저 초기화, 역순 정리)(F-88).
- `Generator`가 `NoCopy`다. `gen().*`처럼 제너레이터 값을 복사하는 코드는 컴파일 오류다. `^Generator` 참조는 그대로 쓴다(F-94).
- 범위를 벗어난 인덱스 · 길이가 panic이다: `Array` · `Slice`의 `remove`, 음수 슬라이스 시작(`a[-1..]`), 음수 길이의 `size_up` ·
  `[]int(n, v)` · `Array[int](n, v)`. 이전에는 일부가 조용히 통과하면서 메모리를 깨뜨렸다(F-93).
- `str.repeat` · `**`는 결과가 4 GiB를 넘으면 `InvalidArgument` panic이다(F-93).
- struct 초기화의 항목은 모두 `name = value`여야 하고(`A{x = 2, 3}`은 오류), `case` 캡처(`|a|`)는 choice의 case에만 쓴다.
  함수 · 람다 매개변수 자리에는 이름이 있어야 한다(F-89).
- 필드 이름 · case 이름이 중복되면 컴파일 오류다(F-81).
- 템플릿 함수 · 컴파일 시간 함수(`print`, `spawn`, `type.size` 등)는 값으로 쓸 수 없다. trait 선언은 값 타입 자리
  (`[]Shape`, `?Shape`, 필드, `Map`의 키 · 값)에 쓸 수 없고 `^Dyn[Shape]`를 쓴다(F-94).
- `i8` · `i16` · `i32`와 `byte` · `r16` · `r32`의 나눗셈 · 나머지 · `>>` · `float()` 변환 결과가 바뀐다. 이전 값이 틀렸다(F-82 · F-84).
- 임베딩: `print` · `eprint` 콜백의 첫 인자가 선언대로 `CLThread*`다. `cyber.h`에서 구현이 없던 선언과 매크로가 바뀌었다
  (`CL_BIND_DECL_TYPE` 등). 컴파일 오류 요약에 터미널 이스케이프 코드가 기본으로 없다(F-50 · F-51 · F-52).

## 버그 수정

- 전역 초기화식이 부른 함수가 아직 초기화되지 않은 전역을 건드려 프로세스가 죽던 것을 막았다(F-88).
  `global a str = foo()` 뒤에 선언한 `global b str`을 `foo`가 읽으면 abort(종료 코드 134), `foo`가 초기화 중인 `a`에 대입하면
  SEGV, 정수 전역은 쓰레기 값이었다. 이제 컴파일 오류다:
  ``The initializer of `a` can reach `foo`, which accesses the global `b`. `b` is initialized after `a`.``
  검사는 이름으로 부른 함수(연산자 · `@init` · `@deinit` 포함)를 따라간다. 함수 값이나 trait를 거친 호출이 하나라도 닿으면
  값으로 쓰인 함수 전부(람다, 변수에 담거나 인자로 넘긴 함수, 제너레이터)와 trait를 구현한 메서드 전부를 도달 가능하다고 본다.
  그래서 실제로는 실행되지 않는 접근도 오류가 될 수 있다. 읽히는 전역을 먼저 선언하면 된다
  (`docs/decisions/project_global_init_order.md`).
- 모듈의 전역이 그 모듈을 가져다 쓰는 쪽보다 늦게 초기화되던 것을 고쳤다(F-88). `use lib './lib.cy'` 뒤
  `global x int = lib.compute()`는 `lib`의 전역이 초기화되기 전에 `compute`를 불러 쓰레기 값을 얻었다. 이제 모듈은 자기가
  `use`로 가져온 모듈 다음에 초기화되고(core가 맨 앞), 프로그램 끝에서는 그 역순으로 정리된다.
- 스크립트가 호스트 프로세스를 끝낼 수 있던 경로 둘을 막았다(F-52). 실패한 적 없는 `cy.VM`에 `compile_error_summary()`를 부르면
  `panic: No report.`, `panic_summary()`를 부르면 `panic: Unexpected panic type.`으로 프로세스가 abort했다(종료 코드 134).
  이제 빈 문자열을 돌려준다.
- 한 타입 안에서 이름이 겹치는 필드나 case가 컴파일러를 죽이던 것을 고쳤다(F-81). `type P: x int, x int`, 같은 case를 두 번 적은
  enum · choice · cunion은 `panic: Unsupported: .field`(`.enum_case` · `.choice_case` · `.union_case`)로 프로세스가 abort했다
  (종료 코드 134). 이제 두 번째 선언 위치의 컴파일 오류다: ``CompileError: `x` has already been declared as a `field`.``
- 타입 선언이 중간에 컴파일 오류로 끝날 때 컴파일러가 메모리를 놓치던 곳 셋을 고쳤다. trait의 메서드 하나가 해석에 실패할 때
  (없는 반환 타입 등) 그 앞 메서드들, enum · choice · cunion의 case 하나가 실패할 때(없는 payload 타입, 중복 이름) case 목록.
  누수는 실패한 eval마다 쌓였고 `cl_vm_deinit`도 돌려주지 않았다.
- 잘못 쓴 선언 넷이 컴파일러를 죽이던 것을 고쳤다(F-89). 모두 종료 코드 134였고 이제 위치가 붙은 오류다.
  (1) 매개변수 이름 자리에 이름이 아닌 식: `fn foo(&self):`, `fn foo(a int, 1):`, `f := fn(^a) => 1`은
  `panic: Expected name.`이었다. 이제 `ParseError: Expected parameter name.`(메서드의 receiver는 `fn (&T) name()`으로 적는다).
  타입만 적는 매개변수는 함수 타입(`fn(&int, ^int) -> int`)에서만 된다.
  (2) struct 초기화의 필드 이름 자리에 숫자: `A{1 = 2}`는 같은 panic이었다. 이제 `CompileError: Expected field name.`
  (3) struct 초기화에 `이름 = 값`과 값만 있는 항목을 섞은 것: `A{x = 2, 3}` · `A{3, y = 2}`는 Bus error였다.
  이제 `CompileError: Expected key value pair.`(`const` 초기화식도 같다).
  (4) choice가 아닌 값의 `switch`에서 payload 캡처: `case 1 |a|:`는 `panic: attempt to use null value`였다.
  이제 `CompileError: Only a case of a choice can capture a payload.`
- `Array`에 `Slice`를 붙이면 스택이 넘치던 것을 고쳤다(F-90). `a := Array[int]{}` · `s := []int{2, 3}` 뒤 `a.append(s)`와
  `a << s`는 `panic: Stack overflow.`였다. `append(arr AsSpan[T])`가 `arr[..]`로 자기 자신을 다시 불렀다(`Slice`를 자른 값은
  다시 `Slice`다). 이제 `arr.span()`으로 원소를 붙인다. `a.append(s[..])`도 같은 경로였다.
- `#[cond=false]`로 빠진 선언이 그 이름의 유일한 선언일 때 그 이름을 쓰면 컴파일러가 죽던 것을 고쳤다(F-91).
  `#[cond=false] fn foo()` 뒤 `foo()`, 메서드 `a.foo()`는 Segmentation fault(종료 코드 134)였다. 빠진 선언이 함수 없는
  빈 심볼을 남겼다. 이제 ``Undeclared variable `foo`.`` · ``Can not find the symbol `foo` in `A`.``다.
- `for a |&i, e|:`처럼 인덱스 자리에 이름 아닌 식을 쓰면 컴파일러가 죽던 것을 고쳤다(F-92). Segmentation fault(종료 코드
  134)였고 이제 `CompileError: Expected a variable name for the index.`다. 빌림 순회(`|i, &e|`)를 넣으면서 `&`가 캡처
  자리에서 파싱되기 시작해 닿게 된 경로다.
- 컨테이너에 범위를 벗어난 인덱스 · 길이를 주면 호스트가 죽거나 메모리가 조용히 깨지던 것을 고쳤다(F-93). 이제 모두
  `panic`이다.
  - `Array.remove(i)` · `Slice.remove(i)`: 범위 검사가 없었다. `i >= len`은 Segmentation fault, 음수는 버퍼 앞쪽을 덮어썼다.
    이제 `Out of bounds index`.
  - 음수 슬라이스 시작: `Array` · `Slice` · span · `Buffer`의 `a[-1..]`가 길이 `len + 1`인 버퍼 밖 구간을 돌려줬다.
    `Span.vec(-1, n)`도 같았다. 이제 `Out of bounds index` · `OutOfBounds`.
  - 음수 길이: `Array.size_up(-1, v)` · `Slice.size_up(-1, v)` · `[]int(-1, 0)`이 길이 `-1`인 값을 만들었고
    `Array[int](-1, 0)`은 호스트가 abort했다. 이제 `Invalid argument.` · `Invalid allocation length: -1`.
  - 너무 큰 길이: `Array[int](1 << 62, 0)` · `[]int(1 << 62, 0)` · `ensure_cap` · `size_up`은 바이트 수 계산이 넘쳐
    Segmentation fault이거나 abort였다. 이제 `Invalid allocation length` 또는 `OutOfMemory`.
  - `'ab'.repeat(1 << 62)` · `'ab' ** (1 << 62)`와 `s.index_rune(1 << 62)`는 정수 변환에서 abort했다. `repeat`은 결과가
    4 GiB를 넘으면 `InvalidArgument`, `index_rune`은 코드 포인트가 아닌 값에 `none`이다.
  - `Buffer[T](n)` · `Buffer[T](n, v)`가 원소 크기를 한 번 더 곱해 필요한 것보다 크게 할당하던 것과, 관리 원소의
    `Buffer.size_down`이 없는 필드 이름 때문에 컴파일되지 않던 것도 고쳤다.
- 타입 · 함수 심볼을 잘못된 자리에 쓰면 컴파일러가 죽던 것을 고쳤다(F-94). 모두 종료 코드 134였고 이제 위치가 붙은 오류다.
  - 함수 시그니처 밖의 `%x`: `type A = %x` · `Array[%x]{}` · `#if %x:` 등. 이제
    ``CompileError: `%x` can only be declared in the signature of a function.``
  - `type` 자리의 한 글자 문자열: `type.size('s')` · `type.name('s')`. 코드 포인트 정수가 타입 포인터로 쓰였다. 이제
    ``Expected argument `type`, found `EvalStr```.
  - 런타임 함수가 없는 함수를 값으로: `y := spawn` · `y := print` · `y := type.size`(템플릿 · 컴파일 시간 함수). 이제
    ``The function `spawn` can not be used as a value.``
  - 함수 심볼에 `^` · `*`: `x := ^f` · `x := *f`는 Segmentation fault였다. 이제 `A function symbol can not be lifted.` ·
    `Can not take the address of a function symbol.`
  - 부모 타입만 있고 이름이 없는 선언: `fn foo[]():` · `global A[] int = 1` · `const A[] = 1`. 이제
    ``ParseError: Expected `::` and a name after the parent type.``
  - trait 선언을 값 타입으로: `type.size(Shape)` · `[]Shape{}` · `?Shape` · `Map[str, Shape]{}` · `Map[Shape, int]{}`,
    trait 타입의 필드, `@unsafeCast(Shape, 1)` · `@unsafeCast(f, 1)`. 이제 ``The type `Shape` has no size.`` 또는
    ``Expected a value type for the parameter. `Shape` is a trait.`` 동적 디스패치는 전과 같이 `^Dyn[Shape]`를 쓴다.
  - `type.info(Shape)`(trait): 이제 ``CompileError: `type.info` does not support the trait `Shape`.``
- 제너레이터 값을 복사하면 종료 때 호스트가 죽던 것을 고쳤다(F-94). `x := gen().*`가 프레임 버퍼를 두 번 해제했다.
  `Generator`는 이제 `NoCopy`라서 ``Cannot copy `Generator[fn() -> int]`, type implements `NoCopy`.``다. `^Generator` 참조를
  넘기고 저장하는 코드는 그대로다.

## 언어와 표준 라이브러리

- (F-82) `i8` · `i16` · `i32`와 `byte` · `r16` · `r32`의 나눗셈 · 나머지 · `>>`가 VM 백엔드에서 틀린 값을 내던 것을 고쳤다. VM 레지스터는 64비트이고
  좁은 정수의 상위 비트는 정해져 있지 않은데(변환과 넘친 덧셈이 그대로 둔다) 세 연산이 그 비트까지 읽었다.
  `i8(-8) / i8(2)`는 `124`, `i32(-8) / i32(2)`는 `0`, `i32(-7) % i32(4)`는 `-7`, `(byte(200) + byte(100)) / byte(2)`는 `0x96`이었다.
  이제 `-4` · `-4` · `-3` · `0x16`이다. `udiv` · `umod`도 같이 고쳐졌다. 비교 연산처럼 연산 앞에서 피연산자를 자기 폭으로 확장한다.
  같은 원인의 `float()` 변환(F-84)과 `**` 컴파일 오류(F-85)는 아래 항목에서 고쳤다.

- (F-84) `i8` · `i16` · `i32`와 `byte` · `r16` · `r32`를 `float` · `f32`로 바꿀 때 넘친 값의 상위 비트가 읽히던 것을 고쳤다.
  `float(i8(100) + i8(100))`은 `200`, `float(byte(200) + byte(100))`은 `300`이었다. 이제 `-56` · `44`다(`int()` 변환과 같은 값).
  부호 있는 정수는 자기 부호 비트에서, `byte` · `r16` · `r32`는 0으로 확장한 뒤 변환한다.

- (F-85) `i8` · `i16` · `i32`의 거듭제곱 `**`이 컴파일된다. 이전에는 `i8(2) ** i8(3)`이 `core.cy`의 `return result`에서
  ``CompileError: Expected type `i8`, got `int`.``였다. 결과는 피연산자 타입이고 넘치면 그 폭에서 wrap한다(`i8(2) ** i8(8)`은 `0`).

- (F-86) 목표 타입이 `float`인 자리의 `~`가 컴파일된다. `float(~x)`, `var f float = ~x`, `float` 매개변수에 넘긴 `~3`, `var o ?int = ~x`가
  ``CompileError: Can not find the symbol `~` in `float`.``(또는 `` in `?int` ``)였다. 목표 타입이 피연산자에 먼저 적용돼 `x`가 `float`로
  바뀐 뒤 `~`를 찾았기 때문이다. 이제 목표가 정수(`Int` · `Raw`)일 때만 피연산자에 전달한다. 정수 목표의 동작은 그대로다:
  `var z r32 = ~r16(5)`는 피연산자를 먼저 넓혀 `0xfffffffa`이고(C의 정수 승격과 같다), `n := ~r16(5)` 뒤 `r32(n)`은 `0xfffa`다.

- (F-83) `Int.asr()`(부호를 유지하는 오른쪽 시프트)가 VM 백엔드에서 동작한다. 이전에는 호출하면 `bc_gen: .asr` 뒤 `CompileError: error.TODO`로
  컴파일이 실패했다. `(-8).asr(1)`은 `-4`다(`-8 >> 1`은 0을 채우는 logical shift라 큰 양수). `i8` · `i16` · `i32`는 자기 폭의 부호 비트에서
  시프트하고, 시프트 양이 부호 비트를 넘으면 부호만 남는다(음수는 `-1`, 아니면 `0`). VM에 `ASR` opcode를 더했다. C 백엔드(`cgen`)에는 아직 없다.

- 전역 초기화식에서 먼저 초기화되는 전역을 이름으로 쓸 수 있다(F-88). `global a int = 123` 뒤의 `global b int = a + 1`,
  가져온 모듈의 전역 `lib.x`, 호스트 전역이 된다. 이전에는 모두 `Cannot reference globals in a global initializer.`였고 함수를
  거쳐야 했다. 뒤에 선언된 전역이나 자기 자신을 쓰면
  ``The initializer of `b` accesses the global `a`. `a` is initialized after `b`.`` `#[extern]` 전역은 여전히 쓸 수 없다.

- (F-87) `Map`의 키로 `i8` · `i16` · `i32`, `byte` · `r16` · `r32` · `r64`, `bool`, `symbol`, `error`, `f32`를 쓸 수 있다. 이전에는 `Map[i8, int]{}`가
  `core.cy`의 `AutoHash`에서 `CompileError: Unsupported: i8`이었다(`int` · `str` · `float` · enum · `Object` · `^T`만 됐다).
  좁은 정수 키는 자기 폭의 값으로 해시하므로 넘친 값(`i8(100) + i8(100)`)과 `i8(-56)`은 같은 키다.

- `int(e)`가 enum 값을 case의 정수 값으로 바꾼다(F-77). 매뉴얼의 Enums 절 예제(`print(int(fruit))  --> 3`)가 `core.cy`의 `Int.@init`에서
  `CompileError: Unsupported: Fruit`였다. `i8` · `i16` · `i32`도 받는다.

- `spawn`의 인자와 반환값으로 `bool`, `float`, `f32`, `byte` · `r16` · `r32` · `r64`, `symbol`, `error`, enum을 보낼 수 있다(F-65).
  이전에는 정수(`int` · `i8` · `i16` · `i32`)와 `str`만 됐고 나머지는 `CompileError: Expected sendable: bool`이었다.
  `?T`, 배열, 맵, `@send`를 선언하지 않은 struct는 여전히 보낼 수 없다.
- (F-91) 템플릿 타입의 메서드에 붙인 `#[cond=…]`가 그 인스턴스의 타입 매개변수를 볼 수 있다.
  `#[cond=type.is_copyable(T)] fn (&Box[]) dup() -> T`는 ``Could not find the symbol `T`.``였다. 조건이 거짓인 인스턴스에는
  그 메서드가 없다(``Can not find the symbol `dup` in `Box[R]`.``). 같은 이름의 오버로드 가운데 첫 선언이 빠져도 뒤의 선언은
  남는다(이전에는 템플릿 인스턴스에서 첫 선언이 빠지면 이름 전체가 사라졌다). `NoCopy` 원소 컨테이너(F-26)의 준비 단계다.
- (F-26) `Array`가 복사할 수 없는 원소를 담는다. `with NoCopy` 타입, `NoCopy` 멤버를 가진 struct, `Array` 자신
  (`Array[Array[int]]`)이 원소가 될 수 있다. 이전에는 `Array[R]{}`부터 core.cy 안의 `Cannot copy` 오류였다.
  규칙은 다른 곳과 같다. 넣을 때는 옮긴다: `a.append(R{id=1})`, `a << R{id=2}`, `Array[R]{R{id=1}, move x}`, `a[0] = R{id=5}`
  (옛 원소는 파괴된다). 읽을 때는 빌린다: `a[1].id`, `r := &a[0]`. `x := a[0]`과 `for a |r|`는 복사라 컴파일 오류다.
  원소마다 `@deinit`은 한 번 돈다. 원소를 복사하는 메서드(`clone` · `last` · `contains` · `index` · `size_up` · `setLast` ·
  `Array[R](n, val)` · span을 붙이는 `append` · `<<`)는 이런 배열에 없다(``Can not find the symbol `last` in `Array[R]`.``).
  `Slice` · `Map`의 원소는 아직 안 된다(`docs/decisions/project_array_nocopy_elem.md`).
- 빌림 순회 `for a |&elem|`을 추가했다. `elem`은 원소의 빌림(`&T`)이고 원소를 복사하지 않는다. 인덱스와 함께는
  `for a |i, &elem|`. `Array`와 `Slice`가 지원한다(`next_borrow(idx &int) -> scope ?&T` 메서드). 복사할 수 있는 원소에도 쓸 수 있고,
  `@deinit`이 있는 원소는 `for a |elem|`과 달리 순회마다 복사 · 파괴가 없다. 순회 중에는 배열을 고칠 수 없다
  (`Expected exclusive access.`). `next_borrow`가 없는 타입은
  `` `Map[str, int]` can not be iterated by borrow. It has no `next_borrow` method. ``

## 임베딩 API

- 메모리 한도: `cl_vm_set_memory_limit(vm, bytes)`와 `cl_vm_memory_used(vm)`(F-41). 한도는 VM이 할당자로 쥔 전체 바이트
  (컴파일러 · 로드된 모듈 · 힙 · 스택, 첫 eval 뒤 약 2 MiB) 기준이고 0 이하는 무제한(기본값)이다. 스크립트에 N 바이트를 주려면
  `cl_vm_memory_used(vm) + N`으로 정한다. 스크립트가 힙이나 스택을 한도 너머로 키우면 `panic: OutOfMemory`이고 eval은
  `CL_ERROR_PANIC`을 돌려준다. panic은 힙 페이지와 커진 스택을 반환하므로 같은 한도로 VM을 계속 쓸 수 있다. `spawn`한 스레드도
  같은 한도를 쓴다(`panic: Spawned thread panicked: OutOfMemory`). 컴파일 단계와 호스트 함수의 할당은 세기만 하고 막지 않는다
  (`docs/decisions/project_memory_limit.md`).
- C 호스트용 메모리 함수: `cl_vm_init_mem(CLMemFuncs)`가 `ctx` · `alloc(ctx, size, align)` · `free(ctx, ptr, size, align)`로 VM을
  만든다(F-41). `CLVM` 객체를 포함해 VM의 모든 메모리가 이 두 함수를 거치고 `cl_vm_deinit`이 전부 돌려준다. `align`은 2의 거듭제곱이며
  `malloc`의 보장보다 클 수 있고, 두 함수는 스레드에 안전해야 한다(`spawn`). 제자리 성장 함수는 없다. 스크립트의 메모리 상한은 `NULL`을
  돌려주는 `alloc`이 아니라 `cl_vm_set_memory_limit`으로 건다. `examples/libcyber/host_tool.c`가 이 방식으로 바뀌었다
  (`docs/decisions/project_c_mem_funcs.md`).
- 호스트 할당자가 eval 중에 실패해도(`cl_vm_init_mem`의 `alloc`이 `NULL`, `cl_vm_initx`에 준 할당자의 실패) eval은 오류를 돌려주고
  VM은 계속 쓸 수 있다(F-41). 이전에는 실패한 지점에 따라 프로세스 abort · SEGV · 누수였다(`docs/decisions/project_compile_alloc_failure.md`).
  - 컴파일러에서 실패: `CL_ERROR_COMPILE`. 요약은 `CompileError: OutOfMemory` 계열(텍스트 writer 뒤의 실패는 `WriteFailed`)이거나,
    리포트를 만들 메모리도 없으면 비어 있다.
    다음 eval · validate는 `cl_vm_reset`처럼 VM을 reset한 뒤 시작한다. `persist_main` 세션이 쥐고 있던 지역 변수와 선언은 사라진다.
    호스트 설정(연료, 스택 · 메모리 한도, 프린터, user data)은 남는다.
  - 스크립트 실행 중 실패: `CL_ERROR_PANIC`, `panic: OutOfMemory`. 다른 panic의 메시지를 할당하지 못하면 메시지가 `OutOfMemory`로
    바뀌고, 스택 트레이스를 기록하지 못하면 트레이스가 비어 있다. 어느 경우에도 스레드의 힙은 해제된다.
  - 실행 뒤 정리(결과 값 복사, `persist_main`의 지역 변수 이월)에서 실패: `CL_ERROR_UNKNOWN`, 요약 없음.
  - `cl_vm_error_summary` · `cl_vm_compile_error_summary` · `cl_thread_panic_summary`는 문자열을 할당하지 못하면 null `CLBytes`를
    돌려준다. `cl_vm_freeb`에 그대로 넘겨도 된다.
  - `cl_mod_add_func` · `cl_mod_add_type` · `cl_mod_add_global`과 타입 생성 콜백(`CLCreateTypeFn`의 `NULL` 반환)의 실패는 그 모듈을
    로드하던 컴파일의 실패가 된다. `clExpandTypeTemplate` · `cl_find_type`은 `NULL`을 돌려준다.
  - 그대로인 것: VM을 만드는 중(`cl_vm_init` · `cl_vm_initx` · `cl_vm_init_mem`)과 호스트가 값을 만드는 함수(`cl_str_init`,
    `cl_array_empty`, `cl_map_empty`, `cl_vm_alloc` 등)의 할당 실패는 여전히 프로세스를 abort한다. 스크립트의 메모리 상한은
    실패하는 할당자가 아니라 `cl_vm_set_memory_limit`으로 건다.
- `cl_vm_allocator`가 돌려주는 할당자는 호스트가 `cl_vm_initx`에 준 것이 아니라 그 위의 계수 래퍼다. 거기서 받은 메모리는 같은
  할당자로 돌려줘야 하고, `cl_vm_deinit` 뒤에는 쓸 수 없다.
- panic으로 끝난 eval은 힙 페이지(첫 페이지 제외)와 main 스레드의 커진 스택을 할당자에 돌려준다. 이전에는 VM이 끝날 때까지 쥐고 있었다.
- 객체 · 클로저 · 함수 union 할당이 실패하면 `CL_ERROR_UNKNOWN` 대신 `panic: OutOfMemory`(`CL_ERROR_PANIC`)다.
- `print` · `eprint` 콜백(`CLPrintFn` · `CLPrintErrorFn`)의 첫 인자가 선언대로 실행 중인 스레드(`CLThread*`)다. 이전에는 VM 포인터를
  넘겨 콜백 안의 `cl_thread_vm(t)` 같은 호출이 쓰레기를 읽었다. 콜백에서 VM이 필요하면 `cl_thread_vm(t)`를 쓴다(F-50,
  `docs/decisions/project_capi_header_sync.md`).
- `cyber.h`를 실제 export에 맞췄다(F-51). 구현이 없던 `clResolveType` · `cl_array_empty_new` · `cl_map_empty_new` 선언을 지우고
  `cl_array_empty(CLThread*, CLType*)` · `cl_map_empty(CLThread*, CLType*)`를 선언했다. `cl_type_from_id`는 `(CLVM* vm, CLTypeId id)`다.
  정의되지 않은 타입을 참조하던 `CL_CUSTOM_TYPE` · `CL_CUSTOM_PRE_TYPE` · `CL_CREATE_TYPE` 매크로는 `cl_mod_add_type`에 넘길
  `CLBindType`을 만드는 `CL_BIND_DECL_TYPE(id)` · `CL_BIND_CREATE_TYPE(fn)` · `CL_BIND_ALIAS_TYPE(fn)`으로 바꿨다. 주석의 옛 이름
  (`cl_free` → `cl_vm_freeb` 등)을 고쳤다. 헤더에 없던 export `clAlloc` · `clGetAllocator`는 지웠다(`cl_vm_alloc` · `cl_vm_allocator` 사용).
  lib 테스트가 헤더의 모든 `cl*` 함수 선언이 export되는지 링크로 검사한다.
- 컴파일 오류 요약(`cl_vm_error_summary` · `cl_vm_compile_error_summary`)에 터미널 이스케이프 코드가 없다(F-52). 이전에는 표시 줄이
  호스트가 무엇이든 `\x1b[31m^~~~\x1b[0m`이었다. 색이 필요한 호스트는 `cl_vm_set_error_color(vm, true)`로 켠다. 설정은 `cl_vm_reset`을
  넘어 유지되고, 스크립트가 만든 `cy.VM`은 부모 VM의 설정을 물려받는다.
- `cl_vm_compile_error(vm, &err)`가 마지막 eval · compile · validate의 컴파일 오류를 `CLCompileError`로 준다(F-52). `kind`
  (`CL_REPORT_TOKEN_ERROR` · `CL_REPORT_PARSE_ERROR` · `CL_REPORT_COMPILE_ERROR`), `msg`(위치 없는 메시지), `uri`, `has_loc`, `line` ·
  `col`(0부터, `col`은 바이트), `len`(그 줄에서 표시되는 바이트 수, 토큰 · 파싱 오류는 1). 마지막 결과가 `CL_ERROR_COMPILE`이 아니면
  false를 돌려주고 `err`를 0으로 채운다. `msg` · `uri`는 VM 소유이고 다음 eval · compile · validate · reset 전까지 유효하다. 컴파일러는
  첫 오류에서 멈추므로 오류는 컴파일당 하나다. 문맥(이전 선언 · 템플릿 호출 지점)은 요약 문자열에만 있다
  (`docs/decisions/project_compile_error_report.md`).
- `cl_vm_compile_error_summary`는 기록된 컴파일 오류가 없으면, `cl_thread_panic_summary`는 스레드의 마지막 실행이 panic하지 않았으면
  빈 `CLBytes`를 돌려준다. 이전에는 호스트 프로세스를 abort했다. 빈 결과는 `cl_vm_freeb`에 그대로 넘겨도 된다.
- `cl_vm_eval`의 헤더 주석을 실제 동작으로 고쳤다. `res`는 `fn main() -> T`의 반환값이거나 `persist_main`에서 마지막 맨 표현식의
  값이고, 값이 없으면 `res_t`가 `CL_TYPE_VOID`다. 성공이 아니면 `res`는 채워지지 않는다. 이전 주석은 설정과 무관하게 마지막 표현식의
  값을 준다고 적었다.

## 변경

- 호환성: 전역 초기화식이 부른 함수가 더 늦게 선언된 전역(또는 자기 자신)에 닿으면 컴파일 오류다(F-88). 이전에는 정의되지 않은
  메모리를 읽었으므로 올바르게 동작하던 스크립트는 없지만, 간접 호출의 보수적 판정 때문에 실제로는 안전했던 스크립트가 거부될 수 있다.
  모듈 사이의 전역 초기화 · 정리 순서도 바뀌었다(가져온 모듈 먼저 초기화, 역순 정리).
- `cyber`가 찍는 컴파일 오류의 표시 줄(`^~~~`)은 stderr가 ANSI 터미널일 때만 빨강이다(F-52). 파이프나 파일로 넘기면
  (`cyber bad.cy 2> err.txt`) 이스케이프 코드가 들어가지 않는다. `NO_COLOR`(비어 있지 않으면 끔)와 `CLICOLOR_FORCE`(비어 있지 않으면
  터미널이 아니어도 켬)를 따르고 둘 다 있으면 `NO_COLOR`가 이긴다. REPL도 같다.
- `cyber compile` 덤프의 `addr` 명령 표기를 `%dst = *%src`에서 `%dst = &%src`로 바꿨다. 이 명령은 레지스터 `src`의 스택 주소를 `dst`에
  넣는 것이라 옛 표기가 역참조로 읽혔다(`docs/decisions/project_ex_borrow_field_addr.md`).
- 빌드 버전 문자열(`cyber version`의 `build-N-xxxxxxx`)을 `zig build -Dbuild=N -Dcommit=xxxxxxx` 옵션으로 넘긴다. `BUILD` · `COMMIT` 환경
  변수는 폴백으로 남지만 Zig 0.17.1의 configure 캐시가 환경 변수를 추적하지 않아 같은 인자의 이전 빌드 결과가 남을 수 있다
  (`docs/decisions/project_fork_release_ci.md`).
- 빌드 · CI의 Zig를 0.17.0에서 0.17.1로 올렸다(`build.zig.zon` `minimum_zig_version`, 워크플로 `ZIG_VERSION`, `Taskfile.yml`, `docs/build.md`).

  `Future[T]`(`Result[Future[T]]` 아님), 없는 `Future.get()` 예제를 `await()`로, `aio` 모듈 · 샌드박스 모드 · safe 모드는

  (컴파일되지 않는다), Attributes 절 작성(속성 9개의 표), `docs/build.md`의 `zig build test-trace` → `trace-test`.

  `TODO: infer tuple type`), `case` fallthrough 예제의 마지막 `case 1000`에 `:`, 함수 유니온 타입 표기 `Func(FN)` → `Func[FN]`와
  그 예제(최상위 `fn`은 지역 변수를 잡지 못하므로 람다로), `!else` 블록은 끝에 도달할 수 없다는 문장.

## 알려진 문제

`docs/study/10-findings-register.md`에 전체 목록이 있다. 스크립트와 호스트에서 바로 닿는 것만 적는다.

- `NoCopy` 원소는 `Array`만 담는다. `Slice` · `ArrayStore` · `Map`은 아직 안 되고, 원소를 배열 밖으로 옮겨 꺼내는
  `pop` · `take`가 없다(`remove`는 파괴한다)(F-26 남은 것).
- VM을 만드는 함수(`cl_vm_init*`)와 호스트가 값을 만드는 함수(`cl_str_init`, `cl_array_empty` 등)의 할당 실패는 여전히
  프로세스를 abort한다. 스크립트의 메모리 상한은 `cl_vm_set_memory_limit`으로 건다(F-41 남은 것).
- `spawn`으로 `?T`, 배열, 맵, `@send`를 선언하지 않은 struct는 보낼 수 없다(F-65).
- `type.info`는 trait 선언을 지원하지 않는다(컴파일 오류). `@unsafeCast`로 제너레이터를 다른 타입으로 바꿔 흘리면 종료 때
  `Unfreed raw buffers` panic이다(F-94 남은 것).
- 순환 참조는 수거도 탐지도 없다(F-43). 에이전트 환경에서는 VM 폐기로 정리한다.
- 호스트 함수 안에서 막힌 호출은 `cl_vm_interrupt` · fuel로 끊지 못한다(F-42).
- `use c` 자체는 막을 수 없다. `deny_raw_ptrs`는 스크립트가 `Ptr` · `PtrSpan` 값을 드는 것만 막는다.
- 정수 값 실수는 소수점 없이 출력된다(`print(3.0)`이 `3`). 배열 루프는 Lua보다 약 2.3배 느리다.
