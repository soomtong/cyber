## 한줄 요약

Cyber 런타임은 "스크립트를 반복 실행하고 호스트 함수로 도구를 노출하며 fuel과 interrupt로 끊는" 에이전트 루프의 기본 형태가 오늘 이미 동작하지만, 호스트 프로세스를 죽이는 경로와 조용한 오답 경로가 남아 있으므로 프로세스 격리와 안전한 스크립트 부분집합을 전제로 쓰고, 그동안 안전망부터 하나씩 메워 나가는 것이 현실적인 흡수 순서다.

## 오늘의 학습 목표

- [ ] 에이전트 루프와 CodeAct 방식이 일반 도구 호출(JSON tool call) 방식과 어떻게 다른지 설명할 수 있다.
- [ ] 이 런타임이 오늘 해 주는 것과 못 해 주는 것을 요구사항 표로 말할 수 있다.
- [ ] "스크립트가 도구 호출을 기다리며 멈추는" 문제의 선택지 다섯 가지와 각각의 비용을 안다.
- [ ] 모델에게 가르칠 안전한 스크립트 부분집합과 그 근거(이슈 번호)를 안다.
- [ ] 흡수 로드맵의 단계와 순서의 이유를 설명하고 첫 기여 과제를 하나 고를 수 있다.

## 1. 왜 이것이 필요한가?

### 1.1 에이전트 루프 (일반 지식)

코딩 에이전트(Claude Code, Codex, opencode, pi 등)의 바깥 구조는 대체로 같은 루프다.

```
        +------------------------------------------------------+
        |                                                      |
   사용자 요청                                                 |
        |                                                      v
        v                                              +--------------+
  [컨텍스트 조립] --> [모델 호출] --> 모델 출력 ---->  | 하네스가 실행 |
        ^                                               +------+-------+
        |                                                      |
        +----------------- 결과를 컨텍스트에 추가 <------------+
```

모델 출력이 "도구 이름과 JSON 인자"이면 도구 호출(tool use) 방식이고, "실행할 코드"이면 코드 실행(CodeAct 계열) 방식이다. 대부분의 상용 코딩 에이전트는 앞의 방식이 중심이다(일반 지식이며 제품별 내부는 확인하지 않았다). 이 저장소의 결정 문서가 가정하는 것은 뒤의 방식이다(`project_direction.md`: "에이전트가 도구 호출을 JSON으로 나열하지 않고 스크립트를 써서 실행하는 CodeAct 계열 설계").

### 1.2 코드로 도구를 부르면 달라지는 점 (일반 지식)

| 관점 | JSON 도구 호출 | 코드 실행 |
| --- | --- | --- |
| 한 턴에 할 수 있는 일 | 도구 호출 목록. 결과에 따른 분기는 다음 턴 | 반복문, 조건문, 변수로 여러 호출을 한 번에 조합 |
| 중간 값 | 매번 모델 컨텍스트를 거친다 | 변수에 남는다 |
| 오류 처리 | 모델이 다음 턴에 본다 | 스크립트 안에서 처리 가능 |
| 위험 | 도구 하나의 권한이 경계 | 임의 코드 실행이므로 격리, 시간 제한, 자원 제한이 필수 |
| 필요한 것 | JSON 스키마 | 작고 안전하고 빨리 뜨는 인터프리터 |

TS/Node 개발자에게 익숙한 비교를 하면 이렇다. 앞의 방식은 REST 엔드포인트를 하나씩 부르는 클라이언트이고, 뒤의 방식은 서버 안에 사용자 스크립트를 올려 두고 내부 함수들을 부르게 하는 플러그인 모델이다. 그래서 두 번째가 훨씬 강력하고 훨씬 위험하다. Node의 `vm` 모듈은 보안 경계가 아니라고 공식 문서가 밝히고 있다(일반 지식). 그래서 Node 안에서 모델이 쓴 JS를 돌리려면 보통 프로세스 분리나 `isolated-vm` 같은 별도 수단을 쓴다. Cyber를 임베딩하는 동기는 이 "작은 별도 런타임"의 자리다.

### 1.3 왜 Cyber를 후보로 보는가 (확인)

`docs/decisions/project_direction.md`와 `project_embedding_agent_loop.md`가 적은 근거를 이 학습에서 확인한 것으로 다시 정리한다.

| 요구 | Cyber의 현황 | 근거 |
| --- | --- | --- |
| 작은 런타임 | ReleaseFast `libcyber.a` 2.1MB(FFI 끔) | 결정 문서 측정 |
| 빠른 시작 | `cl_vm_init` 0.2ms, 첫 eval 2.8~4.4ms(core 청크 컴파일 포함), 이후 eval 14~34µs | 결정 문서 + [08 §5.7](08-embedding-builtins-tests.md) |
| 임베딩 가능한 C API | `cyber.h` 113개 선언. `#[bind]`로 호스트 함수 등록 | [08 §3.1](08-embedding-builtins-tests.md) |
| 실행 제어 | `cl_vm_set_fuel`, `cl_vm_interrupt` | [05 §2.7](05-vm-runtime.md) |
| 오류가 값 | `!T` Result와 `error.Name`. 예외가 없다 | [02](02-symbols-and-types.md), [00](00-language-tour.md) |
| 정적 타입 | 모델이 만든 오류 상당수를 컴파일 단계에서 잡는다(제안: 측정은 안 됨) | [03](03-sema-and-ir.md) |
| 상태 유지 | `persist_main`으로 턴 사이에 지역 변수, 함수, `use`를 이월 | [08 §2.3](08-embedding-builtins-tests.md) |

그리고 반대 증거도 있다. 이 학습에서 찾은 것들이 "프로세스를 분리하고 부분집합을 제한해야 한다"는 결론으로 이어진다(아래 2.4, 2.5).

## 2. 근본적인 동작 원리

### 2.1 오늘 동작하는 구조 (확인: 08장 5.2절에서 컴파일하고 실행한 C 호스트)

08장 작성자가 실제로 만들어 돌린 9턴 시나리오가 오늘의 능력 범위를 잘 보여 준다.

```
 +---------------------------- 호스트 (C) ----------------------------+
 |                                                                    |
 |  cl_vm_init()  --> cl_vm_set_loader(허용 목록)  --> cl_vm_set_printer|
 |        |                                                           |
 |  빈 소스로 한 번 eval (예열. F-04 는 2026-11-08 수정돼 회피 목적으로는 불필요)  |
 |        |                                                           |
 |   매 턴:  cl_vm_set_fuel(100000)                                    |
 |           cl_vm_evalx(소스, persist_main=true)                      |
 |             |                                                       |
 |             +--> CL_SUCCESS          : stdout 수집, 변수 이월         |
 |             +--> CL_ERROR_COMPILE    : 요약(ANSI 제거), 변수 유지     |
 |             +--> CL_ERROR_PANIC      : 요약, 변수 전부 소실           |
 |             +--> CL_ERROR_INTERRUPT  : "Out of fuel.", VM 재사용 가능  |
 |                                                                    |
 |   스크립트 안:  use agent  -->  agent.tool(name, args)  ==> 호스트 함수 |
 +--------------------------------------------------------------------+
```

그 시나리오에서 직접 확인된 동작은 다음과 같다(08 §5.2의 출력).

| 턴 | 입력 | 결과 |
| --- | --- | --- |
| 2 | `n = bump(n)` 두 번, 출력 | `n=2`. 턴 1에서 선언한 `n`이 이월됨 |
| 3 | 호스트 도구 호출 | `{"tool":"read_file","args":{"path":"a.txt"}}` |
| 4 | 구문 오류 | `CompileError`. 이월 변수는 유지 |
| 5 | 이전 변수 사용 | `n still 2` |
| 6 | 호스트가 `cl_thread_ret_panic` | `PanicError`. 이후 변수 전부 소실 |
| 7 | `use os` | `Failed to load module: os`(허용 목록 로더가 거부) |
| 8 | `while true` | `InterruptError: Out of fuel.` |
| 9 | 그 뒤 | `alive`. VM 재사용 가능, 살아 있는 객체 0 |

이것이 "라이브러리 경로는 쓸 만하다"는 결정 문서의 결론을 실행으로 뒷받침한다.

### 2.2 요구사항과 현재 상태

에이전트 루프가 런타임에 요구하는 것을 하나씩 짚고 현재 상태와 근거를 적는다. 위험도는 10장의 이슈 ID를 건다.

| 요구 | 상태 | 근거와 한계 |
| --- | --- | --- |
| 스크립트 반복 실행 | 됨 | 같은 VM에서 반복 eval. 컴파일 오류, panic 뒤에도 VM 유지 |
| 도구를 함수로 노출 | 됨 | `#[bind] fn` + `cl_mod_add_func`. 값 인자는 호스트가 해제(소유 규약이 확정됨, [06](06-memory-ownership.md)) |
| 출력 수집 | 됨, 결함 있음 | `cl_vm_set_printer`. 콜백 첫 인자가 VM 포인터(F-50) |
| 턴 사이 상태 유지 | 부분 | `persist_main`. panic이면 전부 소실, 도구 실패가 곧 세션 손실([08 §7.4](08-embedding-builtins-tests.md)) |
| 시간 제한 | 부분 | `cl_vm_interrupt`(다른 스레드), fuel. 호스트 함수 안 대기는 못 끊음(F-42) |
| 메모리 제한 | 스택만 | 스택 상한 기본 128 MiB · `cl_vm_set_stack_limit`(F-40, 2026-11-08 수정). 힙 한도는 없음, C 호스트용 할당자 훅 곤란(F-41) |
| 모듈 격리 | 부분 | 허용 목록 로더. `math`가 `c`를 쓰므로 함께 열림. `as[Ptr[T]]`로 임의 주소 접근(F-06) |
| 호스트 보호 | 약함 | 컴파일러 panic 경로가 호스트를 abort(F-09. F-08은 2026-11-08 수정), 제너레이터 안 panic(F-03), 첫 eval 실패(F-04, 2026-11-08 수정) |
| 결과 값 수신 | 제한 | `fn main() -> T` 반환뿐. 힙 값 결과의 소유권은 문서화되지 않음 |
| 오류 메시지 | 제한 | 첫 리포트 하나, ANSI 색 코드 포함(F-52) |
| 도구 호출 중 멈춤/재개 | 없음 | 아래 2.3 |
| 병렬 도구 호출 | 거의 없음 | `spawn`은 인자가 int/str뿐, 비-main await는 abort(F-07) |
| 바이트코드 캐시 | 없음 | 호스트 함수 주소가 바이트코드에 박힘(F-54) |

### 2.3 도구 호출을 기다리며 멈추기: 선택지 다섯 가지

가장 큰 간극이다. 스크립트가 `r := agent.tool('read_file', ...)`를 부르면 호스트가 도구나 모델을 호출하고, 그동안 스크립트는 멈춰 있다가 결과가 오면 이어지는 모양이 이상적이다. 07장 6.4절이 코드 근거로 정리한 선택지를 한 표로 모은다.

| 길 | 방법 | 오늘 가능? | 변경 크기 | 한계 |
| --- | --- | --- | --- | --- |
| 1 | 동기 호스트 함수. 도구 함수가 호스트 안에서 블록하고 값을 돌려준다. 세션당 OS 스레드(또는 프로세스) 하나 | 가능. 08장 5.2 데모가 이 방식 | 없음 | 호스트 함수 안에서 막힌 호출은 interrupt로 못 끊는다. 호스트 함수가 같은 취소 플래그를 스스로 확인해야 함 |
| 2 | VM 루프 탈출점. `CALL_HOST`가 "대기" 반환을 받으면 pc를 저장하고 `RES_AWAIT`로 `execBytecode`를 빠져나오고, 호스트가 나중에 결과를 넣고 재개 | 불가(제안, 미검증) | 중간. `cl_vm_resume` 같은 API 추가 | 스크립트 하나가 통째로 멈추는 모델. 호스트 -> 스크립트 -> 호스트 중첩에서는 C 스택이 끼어 멈출 수 없음 |
| 3 | 스택형 `Fiber` 재도입 | 불가 | 큼 | 스택 성장 패치, 빌림, 패닉 규칙, 호스트 프레임 경계 모두 다시 설계 |
| 4 | 제너레이터를 요청 스트림으로. 스크립트 본문을 `#[generator]`로 만들어 도구 호출을 `yield` | 오늘은 안 됨 | F-01 수정이 선행 | 색이 퍼진다(헬퍼 함수 안에서는 yield 못 함). 지역 변수 소실 |
| 5 | Future만으로 | 불가 | | 호스트가 Future를 완료시킬 C API가 없고 main의 await는 spin이라 길 1과 같아진다 |

근거를 한 줄씩 확인으로 적는다. 길 2의 토대는 `execBytecode`가 `t->c.pc/fp`에서 시작하고 `RETURN`이 이를 되돌려 놓는다는 점이다([05 §2.2](05-vm-runtime.md)). `RES_AWAIT -> error.Await -> CL_AWAIT`로 이어지는 반환 경로는 이미 끝까지 연결돼 있고, `RES_AWAIT`를 만들어 내는 곳과 재개 API만 주석 처리돼 있다([07 §2.6](07-coroutines-concurrency.md), [08 §7.4](08-embedding-builtins-tests.md)).

권고(제안): `project_tars_agent_runtime_review.md`의 결론과 같다. 길 1로 시작하고 격리를 프로세스 수준으로 올린다. 길 1이 실제로 모자란다는 증거(승인 대기 중 스레드 점유, 호스트 함수 안 취소 불가)가 쌓인 뒤에 길 2를 시제품으로 만든다. 길 3은 같은 힙에서 여러 실행 맥락이 정말 필요해졌을 때만 검토한다. 길 4는 F-01이 고쳐지기 전에는 쓰지 않는다.

### 2.4 프로세스 격리가 사실상 필수인 이유

이 학습에서 확인한, 스크립트 한 줄이 호스트 프로세스를 죽이는 경로를 모았다.

| 경로 | 예 | 이슈 |
| --- | --- | --- |
| 컴파일러 내부 Zig panic | 한 함수에 지역 변수 257개 · 매개변수 256개 · 구조체 필드 256개 | F-08 (2026-11-08 컴파일 오류로 수정) |
| 같은 계열의 한계 | 아주 긴 루프/if 본문, 65535 초과 점프 | F-09 |
| 제너레이터 안 panic | `#[generator]` 함수가 `panic('boom')` | F-03 |
| 임의 주소 역참조 | `as[Ptr[int]] 8`의 `.*` | F-06 |
| 비-main 스레드 await | `spawn`한 코드 안에서 `await` | F-07 |
| 첫 eval 컴파일 실패 | 다음 eval이 VM을 reset하고 정상 진행 | F-04 (2026-11-08 수정) |
| 무한 재귀 | 스택 상한(기본 128 MiB)에서 `Stack overflow.` panic | F-40 (2026-11-08 수정) |

fuel과 interrupt는 "정상 경로의 폭주"만 잡는다. 위 경로들은 VM이 아니라 호스트 프로세스에서 일어나는 크래시나 abort이므로 VM 수준 제어로는 막을 수 없다. 그래서 설계의 기본 가정은 이렇게 두는 것이 안전하다(제안).

```
   +-------------------+     JSON 줄 프로토콜 (stdin/stdout)    +------------------------+
   | 오케스트레이터     | <------------------------------------> | 워커 프로세스 (자식)     |
   |  (Node/TS 등)      |   {turn, code, limits} / {result}     |  libcyber 임베드        |
   |  - 모델 호출       |                                       |  - 도구 = 호스트 함수    |
   |  - 세션 기록 보관  |        워커가 죽으면 재시작             |  - fuel + 벽시계 타이머  |
   |  - 도구 정책/승인  |        세션 기록으로 재생              |  - 허용 목록 로더        |
   +-------------------+                                       +------------------------+
         OS 수준 격리: 별도 사용자, 파일 시스템 제한, 메모리 ulimit/cgroup
```

설계 요점은 세 가지다(모두 제안이다).

1. 워커가 죽으면 새 워커를 띄운다. `persist_main`의 상태는 워커 안에만 있으므로 잃는다.
2. 상태 복구를 위해 오케스트레이터가 "성공한 턴의 소스"를 순서대로 기록(event sourcing)하고, 새 워커에 재생(replay)한다. 단, 도구 호출에는 부작용이 있으므로 재생 중에는 도구 결과를 기록해 둔 값으로 대체(mock)하거나 멱등한 도구만 허용해야 한다. 이 부분은 설계가 필요한 미해결 지점이다.
3. 스택 한도는 `cl_vm_set_stack_limit`(기본 128 MiB, F-40 수정됨)으로 걸 수 있다. 힙 한도는 런타임이 주지 못하므로(F-41) 프로세스 수준(`ulimit`, cgroup)에서 건다.

TS 개발자 관점의 대응은 `child_process`로 워커를 띄우고 크래시 시 재시작하는 전형적인 패턴이다(일반 지식).

### 2.5 모델에게 가르칠 스크립트 부분집합

`project_tars_agent_runtime_review.md`는 "스펙 문서 4,000토큰 안에 소유권 규칙을 넣지 말고, 복사 가능한 타입만 쓰는 부분집합을 가르치는 쪽이 현실적"이라고 적었다. 이 학습에서 찾은 함정까지 합쳐 프롬프트에 넣을 수 있는 규칙 초안을 만들었다. 각 규칙은 근거가 되는 이슈나 챕터를 가진다. 규칙을 지키게 하는 방법은 프롬프트 설명과, 가능하면 오케스트레이터가 소스를 미리 검사하는 린터 두 가지다(제안).

| # | 규칙 | 근거 |
| --- | --- | --- |
| 1 | `print`는 함수다: `print('x')`. 표현식만 쓴 문장은 오류이므로 반환값을 버릴 때는 `_ = f()` | [00](00-language-tour.md), [08 §5.2](08-embedding-builtins-tests.md) |
| 2 | 값 타입 위주로 쓴다: `int`, `float`, `str`, `bool`, `[]T`. `move`, `&`, `^T`는 쓰지 않는다 | [06](06-memory-ownership.md), tars 검토 |

| 5 | 한 함수의 지역 변수는 256개 이하(2026-11-08부터 넘으면 컴파일 오류. 매개변수 · 구조체 필드는 255개), 문자열 리터럴은 65535바이트 이하, 함수 본문은 짧게 | F-08(수정됨), F-09, F-24 |

### 2.6 오케스트레이터 설계 스케치 (제안, 미구현)

아래는 위 구조를 TS로 표현한 스케치다. 실행해 보지 않았고, 08장의 C 호스트 데모와는 별개로 오케스트레이터 쪽 모양만 보인다.

```ts
// 설계 스케치. 컴파일하거나 실행한 적 없음.
type Limits = { fuel: number; wallMs: number };

type TurnResult =
  | { kind: 'ok'; stdout: string; value?: string }
  | { kind: 'compile_error'; message: string }      // 변수 유지
  | { kind: 'panic'; message: string }              // 변수 소실
  | { kind: 'interrupt'; reason: 'fuel' | 'wall' }  // 변수 소실 (panic 과 같은 경로)
  | { kind: 'worker_crash'; signal?: string };      // 프로세스가 죽음

class Session {
  private accepted: string[] = [];   // 성공한 턴의 소스 (재생용)
  constructor(private spawnWorker: () => Worker) {}

  async turn(code: string, limits: Limits): Promise<TurnResult> {
    const res = await this.worker.run(code, limits);
    if (res.kind === 'ok') this.accepted.push(code);
    if (res.kind === 'worker_crash' || res.kind === 'panic' || res.kind === 'interrupt') {
      await this.rebuild();          // 새 워커 + accepted 재생 (도구는 기록값으로 대체)
    }
    return res;
  }
}
```

판단이 필요한 지점이 두 군데 있다. 첫째, panic과 interrupt에서도 변수가 사라지므로(08 §2.3) 이 둘도 재생 대상이다. 둘째, 재생 중 도구 호출의 처리 방식은 도구마다 다르게 정해야 한다(읽기 도구는 다시 불러도 되고, 쓰기 도구는 기록값으로 대체해야 한다).

## 6. 설계 철학 메모와 흡수 로드맵

### 6.1 원칙 (확인된 이 fork의 방침과 제안)

`docs/decisions/project_direction.md`가 이미 정해 둔 것.

- 용도는 스크립트 실행 CLI와 임베딩 라이브러리다. 네이티브 바이너리, LLVM, JIT는 범위 밖이다. JIT는 `-jit`를 컴파일 오류로 거절한다.
- upstream을 기다리지 않는다. 비어 있는 부분은 이 fork가 설계하고 구현한다.
- 문법은 upstream과 호환을 깨지 않는 범위에서만 바꾸고, 바꿀 때는 `docs/decisions`에 결정을 먼저 적는다.

학습 중 확인한 사실에서 나오는 제안.

- 회귀 테스트를 먼저 쓴다. 이 코드베이스의 큰 버그(F-01, F-20, F-22)는 모두 "테스트가 그 경우를 건드리지 않아서" 살아남았다. 실패하는 모양으로 먼저 고정한 뒤 고친다.
- 소유 규약을 문장으로 먼저 적는다. `docs/history/ownership_memory.md`의 결론이 이미 같다: 버그는 "소유권 모델은 들어왔지만 런타임과 표준 라이브러리가 그 규약을 끝까지 따르지 않은" 자리에서 나왔다.
- 테스트 등록을 점검한다. behavior-test는 수작업 목록이라 20개가 목록 밖이다(F-64). 새 테스트를 만들고 목록에 넣지 않는 실수를 막는 장치(목록 밖 파일을 찾는 검사)가 먼저 필요하다.
- 문서를 믿지 말고 `rg`로 소스에 존재하는지 먼저 확인한다(07, 08장이 같은 결론을 낸다).

- 재현 스크립트를 회귀 테스트로 남겼는가? `behavior_test.zig`의 목록에 등록했는가?

- 릴리스 빌드에서도 디버그 심볼이 필요한 새 명령어인가(F-13, `project_vm_interrupt.md`의 `.jump` 선례)? `pushFCode`를 쓴다.
- ReleaseSafe와 ReleaseFast 두 모드에서 모두 확인했는가? 이 코드베이스에는 모드에 따라 동작이 갈린 선례가 있다(`setOpArgU48`의 8바이트 쓰기가 ReleaseFast에서 메모리를 깨뜨린 일, `project_zig_017_upgrade.md`. F-11의 정의되지 않은 시프트).
- 문서(`docs/docs.md`)와 코드가 달라지는가? 이 코드베이스는 이미 문서와 코드의 차이가 많다. 늘리지 않는다.

## 7. 알려진 이슈와 미완 지점

이 장의 로드맵이 인용하는 이슈는 모두 [10장 종합표](10-findings-register.md)에 있다. 에이전트 루프에 직접 닿는 미완 지점만 다시 적는다.

- 호스트 함수 안에서 멈추고 나중에 재개하는 수단이 없다. `RES_AWAIT` 경로와 `CL_AWAIT` 반환값은 있고 재개 API가 없다.
- 메모리 한도가 없다. C 호스트가 쓸 수 있는 할당자 훅이 없다.
- 샌드박스 모드는 문서에만 있고 소스에 없다. 모듈 허용 목록이 유일한 수단이다.
- `main`이 반환한 힙 값의 소유권이 문서화되지 않았다(08 미확인).
- 이 장의 제안(프로세스 격리, 세션 재생, 부분집합 규칙)은 구현과 측정으로 검증되지 않았다.

## 8. 이해도 확인 Q&A

### Q1. 같은 VM에서 fuel로 무한 루프를 끊을 수 있는데 왜 프로세스 격리를 권하는가?

A: fuel과 interrupt는 VM의 체크포인트(역방향 점프, 호출)에서만 동작하므로 정상 경로의 폭주만 잡는다. 컴파일러 내부 Zig panic(지역 변수 257개, F-08. 2026-11-08 컴파일 오류로 수정), 제너레이터 안 panic 언와인드(F-03), 임의 주소 역참조(F-06), 첫 eval 실패 뒤의 SIGSEGV(F-04, 2026-11-08 수정)는 VM 밖의 호스트 프로세스에서 일어나는 크래시이므로 VM 수준 제어가 개입할 자리가 없다. 스택 한도는 2026-11-08부터 `cl_vm_set_stack_limit`(기본 128 MiB)로 걸리고(F-40 수정), 힙 한도는 여전히 프로세스 수준에서만 걸 수 있다.

### Q2. 오늘 가능한 구조(길 1)에서 "도구 호출을 기다리는 동안 스크립트가 멈춘다"는 것은 어떻게 구현되고, 어디가 모자란가?

A: 도구가 `#[bind]` 호스트 함수이고, 그 함수가 호스트 안에서 블록하다가 값을 반환하면 VM은 `CALL_HOST` 명령에서 그동안 그냥 기다린다(동기 호출). 모자란 곳은 두 가지다. 첫째, 대기 중에는 VM이 체크포인트를 지나지 않으므로 `cl_vm_interrupt`로 끊을 수 없다. 호스트 함수가 스스로 취소 플래그를 확인해야 한다. 둘째, 대기하는 동안 그 세션이 OS 스레드(또는 프로세스) 하나를 점유한다. 세션이 많아지면 비용이 문제가 될 수 있는데 VM당 메모리는 약 2MB라 수십 개는 가능하다는 것이 tars 검토의 측정이다.

### Q3. 제너레이터를 도구 호출 요청 스트림으로 쓰는 방식(길 4)은 왜 지금 쓸 수 없고, 고치면 충분한가?

A: 지금은 제너레이터 본문의 지역 변수가 yield를 넘어 보존되지 않아(F-01) 스크립트가 쓰는 대부분의 변수가 틀린 값이 된다. 고친 뒤에도 두 가지 제약이 남는다. stackless라 모델이 정의한 헬퍼 함수 안에서 도구를 부르면 yield할 수 없어 함수 색이 퍼진다. 그리고 호스트 함수/중첩 호출을 가로지르는 yield가 불가능하다. 즉 길 4는 F-01 수정이 필요조건이지만 충분조건은 아니다.

### Q4. `persist_main`이 panic과 interrupt에서 변수를 모두 버리는 것은 에이전트 설계에 어떤 영향을 주는가?

A: 호스트 도구가 실패를 알리는 수단이 `cl_thread_ret_panic`뿐이라면 도구 한 번의 실패가 세션 전체의 변수 손실로 이어진다. 따라서 도구 실패는 panic이 아니라 반환값으로 모델링해야 한다. 또 fuel 소진도 panic과 같은 경로라 변수를 잃으므로, 오케스트레이터가 성공한 턴의 소스를 기록해 두었다가 새 워커에서 재생하는 방식이 필요해진다. 재생 시 도구의 부작용을 어떻게 다룰지는 미해결 설계 문제다.

### Q5. 안전 부분집합 규칙 3~8, 11~13과 1, 2, 9, 10은 성격이 어떻게 다르고, 그 차이가 로드맵에서 어떻게 쓰이는가?

A: 3~8, 11~13은 런타임에 버그나 한계가 있어서 생긴 임시 규칙이다(제너레이터, spawn, 한계 초과, 오버로드, cte 복합 대입, 포인터 캐스트, trait 검사, 표준 라이브러리 결함, 정수 리터럴 wrap). 해당 이슈가 고쳐지면 규칙을 지울 수 있다. 1, 2, 9, 10은 언어 설계에서 오는 항구적인 지침이다(print 함수 호출, 복사 가능한 값 위주, Option은 안전한 풀기, 실패는 값으로). 로드맵의 각 단계 완료 판정에 "삭제 가능한 임시 규칙"을 넣어, 단계가 끝날 때마다 모델에게 가르칠 내용이 줄어드는지로 진척을 잴 수 있다.

### Q6. 로드맵에서 JIT, LLVM, C 백엔드를 아예 넣지 않은 이유는?

A: `project_direction.md`가 이 fork의 용도를 스크립트 CLI와 임베딩 라이브러리로 정했고 네이티브 산출물을 범위 밖으로 두었기 때문이다. 확인된 사실로, JIT는 `compile()` 맨 앞에서 거절되고 gen.zig는 현재 IR과 맞지 않는 옛 API 그대로이며, `-cc`와 `-tcc`도 sema 단계에서 실패한다(F-33). 에이전트 루프에는 빠른 시작과 작은 크기가 중요하고 이 둘은 바이트코드 VM이 이미 만족한다.

### Q7. 첫 기여로 F-01 수정이 아니라 F-01의 회귀 테스트를 권하는 이유는?

A: 수정은 설계 선택(안 A/B/C)과 여러 파일 변경이 필요하지만, 회귀 테스트는 현재 동작을 명세로 고정하는 작은 변경이다. 테스트가 먼저 실패하는 상태로 있어야 이후 수정이 올바른지 판단할 수 있다. 또 behavior-test가 수작업 목록이라(F-64) 테스트를 등록하는 과정에서 테스트 체계를 함께 배운다. 이 코드베이스의 큰 버그가 모두 "테스트가 그 경우를 건드리지 않았다"는 공통점을 가진다는 점이 이 순서를 정당화한다.
