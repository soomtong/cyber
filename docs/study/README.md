# Cyber 소스코드 1주 학습 가이드

> 대상: soomtong/cyber fork (HEAD b40531a1, 0.4.2-DEV, Zig 0.17.0). 줄 번호와 동작은 이 커밋, aarch64 macOS 기준이다.
> 독자: Node.js/TypeScript 10년차 웹 개발자. 컴파일러, VM, Zig, C 내부는 처음에 가깝다.
> 목표: 이 언어의 설계와 구현을 이해해서 내 프로젝트로 흡수하고, 장차 코딩 에이전트 루프(codex, claude code, opencode, pi 같은 구조)의 실행 언어로 임베딩해 유지보수하는 것.

## 먼저, 질문하신 두 가지에 대한 짧은 답

자세한 근거와 코드 위치는 각 장에 있다. 여기서는 결론만 적는다.

### 0.3에서 0.4로 코루틴 디자인이 어떻게 달라졌나 ([07장](07-coroutines-concurrency.md))

| | 0.3 | 0.4 |
| --- | --- | --- |
| 모델 | fiber 하나. `coinit`/`coresume`/`coyield`. 각자 스택을 가진 stackful 코루틴 | 둘로 갈랐다. 값을 조금씩 내는 쪽은 `#[generator]`와 `yield`(stackless, 프레임 하나만 힙에 저장), 독립 실행은 `spawn`한 Thread + `Future` |
| 장점 | 호출 중간 어디서든 멈출 수 있다. 호스트 경계에서 멈췄다 재개하기에 가장 가까운 모델 | 가볍다(제너레이터 하나 약 146바이트, `next()` 왕복 약 32ns, 실측). 정적 타입과 어울린다. 스택 관리가 필요 없다 |
| 단점 | 객체마다 스택을 가져 무겁고, 동적 타입(`dyn`)에 묶여 있었다 | 호출 중간에서 yield 불가, 함수에 색이 생김, Thread는 int/str만 보낼 수 있고 협력 스케줄링이 없음 |
| 현재 구현 상태 | 삭제됨(`src/fiber.zig`는 죽은 코드) | 제너레이터의 로컬 변수 보존이 구현되지 않아 이 fork에서 실제 스크립트에 쓰면 틀린 결과가 나온다(아래 "가장 중요한 발견") |
| 비어 있는 자리 | | 같은 힙을 공유하는 stackful 코루틴(문서에만 있는 `Fiber`). 에이전트 루프가 가장 필요로 하는 모양이다 |

### 타입 시스템은 어떻게 개편되었나 ([02장](02-symbols-and-types.md))

- 0.3은 동적 타입(`my`/`dyn`)과 정적 타입이 섞인 점진적 타입 언어였다. 0.4는 정적 타입 전용이다. `dyn`, `any`, 동적 메서드 디스패치가 사라졌다.
- 이유는 메모리 모델이다. 값 소유권과 빌림은 수명을 컴파일 시점에 알아야 하는데 동적 타입이 그 전제를 깨뜨린다([06장](06-memory-ownership.md)).
- 그 결과 모든 값의 크기, 정렬, 복사, 소멸 규칙이 컴파일 시점에 정해지고, 릴리스 VM은 런타임 타입 정보를 거의 갖지 않는다. 대신 struct, choice(tagged union), Option `?T`, Result `!T`, trait + `Dyn[T]`, 템플릿(제네릭)이 다형성과 합 타입을 맡는다.
- 정수는 64비트 unboxed다. 힙 박스였던 시기(2024-07)를 거쳐 태그 없는 슬롯 값이 되었다.

## 가장 중요한 발견 다섯 가지

학습 자료를 쓰면서 소스를 읽고 실행해 찾은 것들이다. 전체 목록은 [10장 이슈 종합표](10-findings-register.md)에 있다.

1. 제너레이터의 로컬 변수는 yield를 넘어 보존되지 않는다. 한 줄 요약: `RET_GEN`이 힙에 복제하는 범위가 인자 레지스터뿐이고 `RET_Y`에는 되돌려 저장하는 코드가 없다. 단위 테스트가 힙 객체 상태만 쓰기 때문에 잡히지 않았다(F-01, 07장).
2. 컴파일타임 평가(`const x = f()`)가 복합 대입(`+=`)을 무시해서 같은 함수가 런타임에서는 15, 컴파일타임에서는 5를 낸다(F-20, 03장).
3. 스크립트 한 줄이 호스트 프로세스를 죽일 수 있다: 지역 변수 257개(F-08) · 수천 줄짜리 루프 본문(F-09)(둘 다 2026-11-08 컴파일 오류로 수정), 제너레이터 안 panic(F-03), `as[Ptr[int]] 8`의 역참조(F-06), 첫 eval 컴파일 실패 뒤 다음 eval(F-04, 2026-11-08 수정). fuel과 interrupt는 이런 경로를 막지 못한다. 에이전트 루프에는 프로세스 격리가 사실상 필수다([09장](09-agent-loop-and-roadmap.md)).
4. 힙 메모리 한도가 없다. 스택은 2026-11-08부터 기본 128 MiB 상한에서 `Stack overflow.` panic으로 멈춘다(F-40 수정, `cl_vm_set_stack_limit`).
5. 문서와 코드가 많이 어긋나 있다. `ptr_table`의 용도부터(이 가이드의 초기 가정도 틀렸다) 헤더 선언, 테스트 목록까지. 이 코드베이스에서는 문서를 믿지 말고 `rg`로 소스를 먼저 확인하는 습관이 필요하다.

## 1. 이 가이드를 쓰는 법

- 하루 3~5시간 분량이다. 각 장은 같은 구조다: 한줄 요약, 학습 목표, 왜 필요한가, 동작 원리, 핵심 개념, 소스 읽기 지도, 실습, 변경 관점, 알려진 이슈, Q&A, 더 알아보기.
- 권장 순서: 읽기(개념) -> 소스 읽기 지도를 따라 코드를 직접 열기 -> 실습 실행 -> Q&A로 자가 점검.
- 표기 규칙
  - `src/파일.zig:줄`: 코드로 확인한 사실의 출처.
  - "추정", "미확인": 근거가 약하다는 표시. 고치기 전에 재현부터 한다.
  - "일반 지식": 이 저장소가 아니라 V8, Lua, Rust 등에 대한 설명이므로 코드 사실과 구분된다.
  - "제안": 코드에서 확인한 것이 아니라 설계 의견이다.
- 이 문서에 실린 명령과 출력은 실제로 실행한 것이다. 실행하지 못한 것은 그렇게 밝혀 두었다. 줄 번호가 어긋나면 함수 이름으로 `rg -n 'fn 함수이름' src/`를 다시 검색한다(커밋이 바뀌면 줄 번호는 낡는다).
- `**` 같은 강조 표기를 쓰지 않았다. 이 저장소의 문서 작성 규칙을 따른 것이다.

## 3. 한 장으로 보는 전체 구조

```
  소스(.cy)
     |
     v
 +-----------+   +-----------+   +-----------------+   +---------------------+
 | tokenizer |-->|  parser   |-->| 청크 / 심볼      |-->| sema                |
 | (01)      |   | AST (01)  |   | reserve/resolve |   | 타입 검사 + 소유권    |
 +-----------+   +-----------+   | + 타입, 템플릿   |   | + cte(컴파일타임 평가) |
                                  | (02)            |   | -> IR (03)          |
                                  +-----------------+   +----------+----------+
                                                                   |
                                                                   v
   +-----------------------------------------+        +--------------------------+
   | 런타임                                    |        | bc_gen (04)              |
   |  vm.c execBytecode (05)  <---------------+--------| IR -> 바이트코드         |
   |  heap / ARC (06)                         | u16    | 레지스터 할당, 호출 규약  |
   |  generator / Thread / Future (07)        | 명령   +--------------------------+
   |  host 함수 (#[bind]) <-> libcyber (08)   |
   +-----------------------------------------+
        ^
        |  cl_vm_eval, fuel, interrupt (08, 09)
   호스트 프로그램 (에이전트 오케스트레이터)

   보조: src/builtins/core.cy = 표준 타입을 Cyber 코드로 작성, 매 실행마다 컴파일 (08)
```

핵심 포인트 세 가지.

- 컴파일러의 마지막 입력은 AST가 아니라 sema가 만든 IR이다. 소유권(retain/release/destruct)은 이미 IR에 박혀 있어 `bc_gen`은 번역만 한다.
- 바이트코드 VM은 레지스터 기계이고 인터프리터 루프는 Zig가 아니라 C(`src/vm.c`)로 쓰여 있다. Zig는 `vm.c`를 translate-c로 가져다 쓴다.
- 표준 라이브러리의 큰 부분이 `core.cy`(4.4K줄)에 Cyber로 작성되어 매번 컴파일된다. 그래서 빈 프로그램도 첫 실행에 약 3ms가 든다.

## 4. 환경 준비 (실행으로 확인한 명령)

```sh
# Zig 0.17.0 필요
zig version                                   # 0.17.0

# CLI 빌드 (ReleaseSafe). 첫 빌드는 translate-c 패키지 때문에 네트워크가 필요하다
zig build cli -Doptimize=ReleaseSafe          # zig-out/bin/cyber (옆에 src/ 가 생긴다)

# 추적용 빌드: 컴파일 각 단계 로그와 런타임 트레이스. 기존 산출물을 건드리지 않게 prefix 분리
zig build cli -Dtrace=true -Doptimize=ReleaseSafe --prefix /tmp/cyber-trace

# 실행, 바이트코드 덤프, 트레이스
./zig-out/bin/cyber file.cy
./zig-out/bin/cyber compile file.cy
/tmp/cyber-trace/bin/cyber -v file.cy > /tmp/x.trace 2>&1   # 출력이 7만 줄 이상이므로 파일로 받아 rg로 거른다

# 개별 테스트 (통과하면 출력 없이 exit 0)
./zig-out/bin/cyber src/test/concurrency/generator.cy

# 무한 루프가 걱정되는 실험은 타임아웃과 함께 (macOS에는 timeout 이 없다)
perl -e 'alarm 5; exec @ARGV' ./zig-out/bin/cyber file.cy
```

테스트 스텝(`build.zig`)은 `zig build test`(전체), `behavior-test`, `lib-test`, `lib-standalone-test`, `cli-test`, `trace-test`다. 08장 작성자가 `lib-test` 53/53, `cli-test` 5/5, `lib-standalone-test` 통과를 확인했다. `behavior-test`와 `trace-test`, 전체 `zig build test`는 이 가이드를 쓰는 동안 실행하지 않았다. 9장 로드맵의 0단계가 그 기준선을 만드는 일이다.

문법 주의 두 가지: `print`는 함수 호출이다(`print('hi')`, 0.3의 `print x`는 파싱 오류). 제너레이터 반복은 `while g.next() |v|:` 형태다.

## 8. 이 가이드의 한계

- 실험은 aarch64 macOS, Zig 0.17.0, ReleaseSafe와 trace 빌드에서만 했다. x86-64, Linux, WASM, ReleaseFast에서의 동작은 대부분 확인하지 못했다. 챕터마다 "추정/미확인" 목록이 있다.
- 일부 이슈는 코드 판독으로만 확인했다. 10장의 검증 열을 보라. 고치기 전에 재현부터 한다.
- 챕터는 서로 병렬로 작성되었다. 같은 개념의 서술이 장마다 약간 다를 수 있으나 호출 프레임, `.?` 의미, `ptr_table` 용도, 제너레이터 보존 문제는 장 사이에서 교차 확인했다.
- 로드맵의 규모 추정과 오케스트레이터 설계는 제안이며 구현이나 측정으로 검증되지 않았다.
